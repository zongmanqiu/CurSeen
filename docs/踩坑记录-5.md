### §17.15 「硬件编码」谎报：把"允许了"当"用了"（2026-10-09）

- **背景**：用户问「视频模块的设置都有效吗」。审计发现 `create_sink_writer` 返回
  `(sink, allow_hw)`——`MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS` 只是**允许** MF
  用硬件 MFT；本机没注册硬件编码器时 MF **静默**选软件 MFT，而回落路径也返回
  `true` ⇒ 收尾日志「已启用硬件编码」和 UI 结论全在撒谎。
- **修法**：开工前先 `MFTEnumEx(MFT_ENUM_FLAG_HARDWARE)` 查注册表里有没有硬件
  H264 编码器（复用 `hardware_encoder_name_inner`）：没有直接走软件路径并打
  info，不空跑注定失败的尝试；返回值 = `want_hw` = 真实结论。
- **实测**（探针 `tests/probes/settings_audit.rs`，GTX 1660 SUPER）：
  硬件编码器 = "NVIDIA H.264 Encoder MFT"；Auto 进程 CPU 增量 **2.05s** vs
  Off **5.78s**（各录 5s，2.8 倍差）——硬件编码真实生效。fps15 录 5s = 74 帧
  （目标 75）、max_long_edge=1280 产物 1280×720，全部命中。
- ★ 教训：**"允许"≠"启用"**。凡是"设了个开关就报告成功"的报告链，回落/静默
  路径都会让报告失真；报告值必须来自对实际状态的查询，不是对策略意图的复述。

### §17.16 采集端"原生格式直通"：下游全链 48k×2ch 假设的隐形赌注（2026-10-09）

- **背景**：用户关掉降噪仍觉得录出的声音"接近原声但怪怪的"。排查链路上还会
  "动声音"的环节时发现：`init_and_capture` 按 `GetMixFormat` **原样**采集，
  但下游三处全部硬编码假设 48k×2ch——①两路逐样本求和混音；②
  `write_audio_samples` 时长折算 `48000*2`；③RNNoise `FRAME_SIZE=480`（48k 帧）。
  本机实测恰好都是 48k×2ch×32f（`mix_formats` 探针）所以一直没炸；设备混音
  格式换成 44.1k / 单声道的机器上，产物会**变速/变调/声道错乱**——症状正是
  "接近原声但怪怪的"。
- **修法**（对齐开源同行）：采集端不再用 `GetMixFormat`，改构造固定
  `WAVEFORMATEX`（48k/2ch/16bit）+ `AUTOCONVERTPCM|SRC_DEFAULT_QUALITY` 让
  WASAPI 引擎自己转换（Rivulet `device_capture.rs`、wcap 同款做法）。采集恒定
  48k/2ch/16bit，下游假设永远成立；顺带消灭 f32→i16 手工转换路径。
- **验证**：`audio_echo` 6/6 通过，速率 0.983~0.993 倍不变；全量门禁 1202 passed。
- ★ 教训：**"本机没炸"≠"没有 bug"**——整条下游共享一个从未被显式声明的格式
  假设时，这个假设就必须在源头（采集初始化）钉死，而不是靠设备恰好配合。
  同场加映：离线 A/B 实测 MF AAC 128k 编码偏差 RMS≈1.5/32768（约 -87dB），
  320k 降至 0.87——编码损失存在但远在人耳阈值下，128k 不是音质问题主因。

### §17.17 双回归：面板贴图纹理缺 GDI_COMPATIBLE；悬浮标迁移播种旧参数形状（2026-10-09）

- **回归一（放大镜/画中画录不进视频）**：§17.14 的 clean/work 重构把面板合成
  （`composite_pip_frames`→`blit_pip_frame`，走 `IDXGISurface1::GetDC`）从 `acq`
  挪到 `clean`，但 `clean` 创建时 `misc=0`——`GetDC` 要求
  `D3D11_RESOURCE_MISC_GDI_COMPATIBLE`，缺了每帧 `DXGI_ERROR_INVALID_CALL`
  （日志 1654 条 "pip blit 失败"），面板从此从录制帧里消失。修：`clean` 创建
  补上该标志（`show_cursor=false` 时 `read_tex` 读的正是 clean，只给 work 加
  覆盖不了）。验证：`rec_pip_share` 探针 3 帧面板区 99.7% 纯红。
  ★ 教训：**把一段 GDI 绘制挪到新纹理上时，"目标纹理必须 GDI_COMPATIBLE"
  是绘制通道的属性，不跟着代码走**——原纹理有、新纹理没有，编译期毫无感知。
- **回归二（悬浮标实心圆启动即不透明 #FF0000）**：`migrate_hover_settings`
  在 `hover_params` 为空时播种的是**旧架构参数形状**（6 位色 + 独立 opacity
  键），而现行 schema（solid.lua/ring.lua）的透明度在**颜色里**（8 位
  #RRGGBBAA，opacity 参数已删）。脚本 `hex_to_rgb` 对 6 位色取 a=255 ⇒
  每次启动都复活一个不透明红圆；"切换效果再切回来"走"换脚本即刷新"（重建
  空表 → schema 默认 #FF000040）反而变透明——用户观察完全吻合。
  修：迁移改播 8 位色（alpha 折进颜色）、删 opacity/size 死键、png 改
  scale；且 `cursor_mode=0`（UI 永不更新的遗留快照）不再覆盖 hover_enabled
  （此前把磁盘上的 true 每次启动都按回 false）。判据入
  `legacy_cursor_fields_migrate_into_hover_params`。
  ★ 教训：**"修复默认值"修不掉"每次启动重新播种毒默认值"**——迁移函数是
  一个独立的默认值来源，只查"出厂字面量"一处不够，还要查"迁移会播种什么"。
- 用户疑问的澄清：数值只存 exe 同级 `config.json` 一处，没有别的读取源；
  问题不在"多份配置"，在**迁移播种的形状过时**。

### §17.18 全屏放大录制闪烁（原屏↔放大交替）：seqlock 撕裂帧直接丢弃（2026-10-09）

- **症状**：录屏时全屏放大不再平滑，产物在"原屏幕"和"放大画面"之间来回切换
  （真产物 `CurSeen_2026-10-09_14-11-57.mp4`；运行日志无 blit 失败）。
- **根因**：`capture_share` 是 seqlock 单缓冲：写端每帧 `seq+1→整块写→seq+1`，
  读端前后 seq 一致且为偶数才收。画中画窗口小（几十 KB，写窗口微秒级）从没
  撞过；**全屏放大每帧重写整屏 BGRA（1920×1080×4 ≈ 8MB）**，写窗口毫秒级，
  30fps 消费者（读也是 8MB 拷贝）撞上写中/读中被改写的概率大增——撞上就
  `None`，该帧录制出**没有放大画面的裸桌面**，产物于是交替。
  旧注释"本轮丢弃，下帧再来"隐含假设"撕裂是偶发孤帧"——写端吞吐越高这个
  假设越不成立。
- **修法**：`read_frame` 返回三态 `SlotRead::{Ready, Torn, Empty}`（撕裂 ≠
  没画面，`invalidate` 走 `LEN=0` 与撕裂区分）；`snapshot()` 维护每标题
  "上一帧好帧"缓存：`Torn` 复用上一帧，`Empty` 清缓存；`set_enabled(false)`
  连读者缓存一起清，防上一场画面残留到下一场。
- **验证**：`rec_pip_share` 端到端 3 帧面板区 99.7% 纯红。另
  `fullscreen_zoom_probe` 有 4 例红——全挂在"窗没出现在屏上"的**前置**
  （`pip_window::present` 出画路径，不经过本次改动的读取路径；真正走共享
  链路的"不套娃"用例通过），属环境性前置失败，待后续单独排查。
- ★ 教训：**"失败就丢弃下帧再来"只对小载荷成立**；载荷大到与消费节奏同
  量级时，丢弃率≈写占空比，必须换成"读旧值"语义（seqlock 的标准用法就是
  撕裂时读上一版，而不是没有上一版）。

### §17.19 文字贴图恒为满宽横条：位图宽度没按文本内容收紧（2026-10-09）

- **症状**：剪贴板文字贴图后，图片宽度经常是最大宽（520 逻辑像素）的横条——
  两个字也是全宽，只在中长文本时才"碰巧"看着合理。
- **根因**：`text_raster::render_text` 把 `wrap_w = max_w - 2*PAD` **既当换行
  上限又当成品位图宽度**：`DT_CALCRECT` 只量高度，宽度直接取换行框宽。
  换行上限取满宽没错（尽量少换行），但**成品宽度应该跟随文本实际宽度**。
- **修法**：画之前先用 `GetTextExtentPoint32W` 按显式 `\n` 逐行量自然宽度取
  最长行；最长行放得下（≤ max_wrap）就按它收窄贴图，放不下才用 max_wrap
  换行。短文本（"你好"≈56px）不再撑成 520px 横条。
- **判据**：`short_text_fits_its_content_not_the_max_width`（"你好" @800 上限
  ⇒ 宽 <200 且 ≥ 字宽+2*PAD）。既有 5 例全绿（长文本换行/显式换行/白底等）。
- ★ 教训：**"换行框宽"是排版约束，不是成品尺寸**——用同一根 rect 量高又定
  宽，就把约束泄漏成了输出。

## 二十、覆盖层 DPI 两套换算源分家：特效不落在鼠标上（2026-10-10）

**现象**：用户反馈拖尾/悬浮标/点击效果整体偏离光标（实心圆在光标左上），且
「离虚拟屏原点越远偏得越多」；反馈者**重启电脑后自愈**，单屏机器无法复现。

**根因**：覆盖层里「世界(物理)→逻辑」与「逻辑→物理」用了两个不同的 DPI：

- `WorldMap` / `translate_offset` 的 scale 取 `GetDpiForSystem()`（系统 DPI），
  且 **`lib.rs` 启动时读一次虚拟屏、`run_overlay` 算一次 scale 后冻结，运行期零刷新**；
- 真正光栅的 `SkiaCanvas` 用 `GetDpiForWindow`（windui 随 `WM_DPICHANGED` 更新）。

本进程是 `PER_MONITOR_AWARE_V2`，MS 明确 PMv2 线程不该用 `GetDpiForSystem`。
两值一不等：`上屏位置 = 光标 × (窗口DPI / 系统DPI)`，朝虚拟屏原点收缩或外扩。
任何程序触发显示器有效 DPI 变化（切分辨率、远程桌面/向日葵、插拔屏、投影），
Windows 给全部顶层窗发 `WM_DPICHANGED`——canvas 跟着世界走了，CurSeen 的冻结值
掉队，唯独特效歪。**这就是"重启就好"的全部原因**，与双屏无关。

**修复定式**：`OverlayCanvas::sync_view` 每帧以 **canvas 自己为唯一真相**反推
`scale = 1/canvas.dpi_scale()`、按当前虚拟屏重算 `dx/dy`（`paint` 最开头执行，
不留一帧错配）；DPI 取 0 时兜 1.0（防 scale=inf → 坐标 NaN → 特效整个消失）。

**判据**：`render.rs::dpi_offset_tests` 三条（mock 注入 system=1.5 / actual=1.0，
偏移逐位等于 `光标×(1/1.5−1)`；DPI 一致时必须为 0；反向时外扩）+
`overlay.rs::tests::sync_view_*` 三条（启动 1.5、canvas 变 1.0 ⇒ scale 必须跟到
1.0；DPI=0 兜底）。

- ★ 教训一：**PMv2 下别用 `GetDpiForSystem` 做坐标换算**，`GetDpiForWindow` 才与
  光栅同源。
- ★ 教训二：**DPI / 虚拟屏不是启动常量**——凡与显示相关的量，要么每帧对账，
  要么挂 `WM_DPICHANGED` / `WM_DISPLAYCHANGE` 刷新；冻结在启动值迟早分家。
- ★ 教训三（判据纪律）：单测首版断言"x、y 各自无偏差"直接红——y 与 x 受
  **同一个比例**支配，不是两个独立量；判据红时先怀疑判据。

## 二十一、剪贴板 CF_HDROP：`DragQueryFileW` 会在系统 DLL 内解引用不可信数据而崩（2026-10-11）

**现象**：启动后约 20 ms、且用户只开了「截图与贴图 + 剪贴板」时进程直接消失。
崩溃报告：0xC0000005（**读**无效地址 `0x28568BF25D0`，一个已释放/无效的堆地址），
出错线程 `clip-cmd`（剪贴板后台命令线程），故障点在 **`Windows.Storage.dll`**。

**根因**：扫描剪贴板时遇到别人放的 `CF_HDROP`，照惯例调
`shell32!DragQueryFileW(hdrop, 0xFFFFFFFF, None)` 取条数。该 API **直接按数据头里的
`pFiles`（字符串区起点）去解引用**，而剪贴板里的数据是**别的进程**写的，`pFiles`
可能是乱值——崩在 `Windows.Storage.dll!DragQueryFileAorW`（Win11 上 shell32 的这条
链就落在这个 DLL 里）。系统 DLL 内部崩，我们既拦不住、也救不回来，进程必死。

**修复定式**：数据已经 `GlobalLock` 在我们手里，**自己按界解析 DROPFILES**（20 字节头
+ 双 NUL 结尾的字符串表），彻底不进 shell32：
`GlobalSize` 先看总长（< 22 直接弃）→ `pFiles` 必须落在 `[20, len-2]` → 每条必须
在缓冲内遇到收尾 NUL（没遇到 = 畸形，返回 None）→ 条数硬上限 512（防"永远不到头"）。

**判据**：`clipboard_history::tests::dropfiles_*` 三条纯逻辑单测（宽/ANSI/空列表解析；
`pFiles` 越界 / 落在头前 / 缺结尾 NUL 必须判 None；全 'A' 缓冲不许死循环）。

- ★ 教训一：**剪贴板里的数据一律当"来源不可信"**——先按 `GlobalSize` 定界，再解析
  （与 2026-10-11 修的 `get_text`/`get_image` 越界读是同一类问题）。
- ★ 教训二：**能自己解析就别交给系统 API 去解引用外部数据**。`DragQueryFileW` 是为
  拖放（自己进程收到的、格式可信的 HDROP）设计的，拿它读剪贴板越界了责任在我们。

**复现手段（已实测 100% 命中，2026-10-12）**：`temp/repro_hdrop.py put --mode bad_ptr`
往剪贴板放一条 `pFiles=0x40000000` 的畸形 DROPFILES，再用
`temp/repro_verify.py <exe> <log目录> --mode bad_ptr` 启动被测 exe（启动即扫剪贴板，
与原崩溃同一条路径）。旧版必崩（`windows.storage.dll+0x5D7F24 → curseen.exe+0xB69DF`，
与线上崩溃逐帧一致），新版安全跳过。另备 `bad_ptr_far / no_nul / truncated` 三种畸形
与 `normal` 对照组。
- ★ 做对照实验时**先确认被测目录的 `config.json` 里 `clipboard.enabled=true`**——出厂
  默认是 `false`，功能关着不会去扫描剪贴板，会得到"不崩"的**假阴性**。
- ★ 旧版 exe 若在 `HKCU\...\AppCompatFlags\Layers` 里被标了 `RUNASADMIN`，`CreateProcess`
  会直接失败（WinError 740）⇒ 复制到中性路径再测（程序自身会 runas 提权重启）。

## 二十二、`strip = true` 会让 PDB 里没有本 crate 的符号（2026-10-11）

**现象**：崩溃 minidump 拿到手、同次构建的 `curseen.pdb` 也在，却只能解出
`alloc::` / `core::` 的函数名，**我们自己写的函数一个都解不出来**（PDB 里搜
`read_files_opened` / `clipboard_history` 命中 0）。dbghelp 的 `SymLoadModuleEx`
在本机恒失败（err 18），没有 WinDbg/cdb，只能靠自写解析。

**根因**：`[profile.release]` 只写了 `strip = true`、没开 `debug` ⇒ 生成的 PDB 里
**不含本 crate 的调试信息**（剩下的那 4214 条是 std/alloc 与 MSVC 库的符号）。

**修复定式**：profile 里补 `debug = 1`（行表）。★ **MSVC 下调试信息只进 PDB、不进
exe——实测 exe 体积 6972416 → 6972416（零增长）**，与「体积优先」不冲突，
`strip` 继续保留。配套：deploy 已把每版 PDB 归档到 `temp/symbols/`（重编不失配）。

**判据**：`cargo build --release` 后 `temp/target/release/curseen.pdb` 里能搜到
`curseen_ui::` / 具体函数名（实测 6990 处），且 exe 字节数不变。

- ★ 教训一：**`debug` 与 `strip` 不是一回事，别互相替代**；要"崩溃能定位"必须开 `debug`。
- ★ 教训二：**开了 `debug` 之后 `.text` 会与无调试版本分叉**（实测首字节差异在 0xB3：
  link.exe 关掉了 ICF 折叠，`.text` 大 448 字节）⇒ **旧崩溃的 RVA 不能用新 PDB 解**，
  符号必须按"同次构建"归档（这就是 `temp/symbols/` 存在的原因）。
- ★ 教训三（工具）：无 WinDbg 时可用自写脚本定位——
  `temp/unwind.py`（按各模块 `.pdata` 做 x64 栈回溯，等效 `k`）、
  `temp/funcscan.py`（函数边界 + 函数体内的导入调用）、
  `temp/expnear.py`（系统 DLL 内 RVA 的最近导出名）。

## 二十三、剪贴板：本进程内 `OpenClipboard` 不互斥，写者能把读者正在拷的内存整块抽走（2026-10-13）

**现象**：只开「截图与贴图」+「剪贴板」两个模块时，用着用着进程直接消失（0xC0000005）。
崩溃报告指向 `clipboard.rs:160`（32bpp DIB 逐行 `copy_from_slice`），出错线程
`clip-thumb`。栈上读出 w=1599 / h=819 / stride=6396，越界地址 = 块头 + 510 行
⇒ 那块内存实际只剩 510 行可读，头里却写着 819 行。

**根因**：**不是数据畸形**。`OpenClipboard` 只对**跨进程**互斥，**同进程内不互斥**
（探针实测两个线程能同时打开成功）。程序里有 6 处写点、多处读点、跨 3 个线程，
写者一句 `EmptyClipboard()` 就把读者正在 memcpy 的那块内存整块释放
（页表可读 5,238,720 → 0）。**`GlobalLock` 挡不住这件事**。
★ 上一版的误诊：把 `GlobalSize` 当"不可信"去夹长度——基线实测 `GlobalSize`
声称 5,238,364 与页表可读 5,238,720 完全一致，**它从来没说谎**。夹取的代价是把崩溃
降级成静默返回 `None`（数据在用户毫不知情的情况下丢失）。

**判据**：
- 探针 `tests/probes/clip_race.rs`：三问——① A 打开后 B 仍能打开；② 写者
  `EmptyClipboard` 后读者手里那块可读长度归 0；③ 基线（无写者）`GlobalSize` 与页表一致。
- 差分复现探针 `tests/probes/clip_crash_repro.rs`：旧版逐字代码 → 退出码 0xC0000005
  且落在 `memcpy.asm`；新版真出货函数 → 退出码 0 且 200 次读**像素逐字节一致**
  （这一条排除了"不崩但静默丢内容"这种假绿）。
- **真机复现**（窗口是毫秒级，手按 Ctrl+C 命中率是个位数百分点，别靠运气）：
  PowerShell STA 循环 `Clipboard::SetImage` 大图（`temp/clip_stress.ps1`，
  默认 1600×900 / 间隔 100ms / 300 次）——每次写入都会释放上一块，撞进拷贝窗口。
  实测起跑后约 1.6 秒（第 16 次写入）即崩。
  ★ 脚本**必须带 UTF-8 BOM**：无 BOM 时 Windows PowerShell 5.1 按 GBK 解码中文，
  会把脚本读坏（`ParseFile` 报"缺少右 }"）。

**修复定式**：剪贴板读写**全部**走 `platform::clipboard::with_clipboard` / `lock_clip`；
`hygiene_scan.py` 第 4 查拦裸 `OpenClipboard`（只豁免 `src/platform/clipboard.rs`）。

- ★ 教训一：**从一个"资源"的属主关系去修，不是一个函数一个函数加防御**。4 条读取路径
  （text / DIB / HTML / HDROP）里只护 2 条，race 会从没护的洞里冒出来——而其中
  CF_HDROP 那条正是 10-11 已经崩过一次的老路（当时只换了解析函数，没碰底下的竞态）。
- ★ 教训二：**先证伪自己的前提再写代码**。上一版把"我读出了崩溃地址"当成"我找到了根因"，
  结果在同一处又崩一次。写下预测、做实验、允许自己的旧结论被推翻。
- ★ 教训三：**别把"响亮的崩"改成"安静的丢东西"**——那不叫修复，叫降级。修复的判据
  必须同时包含"没崩"和"内容仍然对"。

## 二十四、`wide()` 的临时 `Vec` 写进 struct literal：借用检查器看不见的悬垂指针（2026-10-13）

**现象**：崩溃过一次之后重启，进程在任务管理器里活着，但**没有托盘、界面出不来**，
只能强杀。日志：`panic: clip panel window: Error { code: HRESULT(0x8007057F),
message: "找不到窗口类。" }`。**时好时坏**——同一份 exe 有时正常。

**根因**：`register_class` 里
```rust
let wc = WNDCLASSEXW { lpszClassName: PCWSTR(wide(name).as_ptr()), ..Default::default() };
RegisterClassExW(&wc)
```
`wide()` 返回的临时 `Vec<u16>` 在 `let wc = ...;` 的**分号处就被 drop**，下一句
`RegisterClassExW(&wc)` 拿到的是已释放的堆地址。因为是 `.as_ptr()` 而不是借用，
**借用检查器看不见它** ⇒ 编译静默通过；堆刚释放时字节通常还在 ⇒ 时好时坏。
链条：类名注成乱码 → `CreateWindowExW` 报 1407 → `.expect()` panic →
`CMD_HWND` 永不置位 → 主线程 `while CMD_HWND.get().is_none()` 死等 → 僵尸进程。

**修复定式**：先 `let name_w = wide(name);` 绑到局部变量再取址（或直接用 `w!` 静态串）。
`hygiene_scan.py` 第 5 查拦 `lpsz*Name: PCWSTR(wide(`。全仓 8 处窗口类注册点只有这一处是坏的
（其余 7 处要么用 `w!`、要么先绑了局部变量）。

- ★ 教训：**`.as_ptr()` 会绕过借用检查**——凡是"临时量取地址后还要跨语句用"的写法，
  编译期零告警、运行期靠运气。写 Win32 结构体字面量时尤其要盯住 `lpsz*` 字段。

## 二十五、解 minidump：`ThreadContext` 的 RVA 在 +164 不是 +160（2026-10-13）

**现象**：自写脚本解析 dump，异常码与访问地址都对，但**寄存器全是 0、`Rsp=0`**，
于是栈回溯整个哑掉（扫不到任何帧）。

**根因**：`MINIDUMP_EXCEPTION_STREAM` 布局是 `ThreadId(4) + align(4) +
MINIDUMP_EXCEPTION(152)` ⇒ `ThreadContext` 的 `DataSize` 在 **+160**、`RVA` 在
**+164**。习惯性取 `+160` 拿到的是 DataSize，把它当 RVA 去读，解出来自然全是 0。

**判据 / 定式**：`temp/_symz_new.py <dump>` —— 自动从 dump 的模块表取主模块基址，
配 `temp/pdbwork/`（同次构建的 exe + 改名成 `curseen.pdb` 的符号）用 dbghelp 精确到
`文件:行号`。★ dbghelp 在本机**其实可用**（此前"恒失败 err 18"是把 exe 路径写成了
不存在的 `build/curseen.exe`）；exe 与 pdb 必须**同次构建**。

- ★ 教训（比对法）：判"复现出来的崩溃是不是同一处"，看**调用链 RVA 是否一致**，
  **不要看 `memcpy.asm` 的行号**——memcpy 按拷贝长度走不同分支（SSE / AVX / erom），
  块大小不同就落在不同行。本次真机复现与 10-12 现场崩溃：调用链 RVA
  `0xD7A2D / 0xD344C / 0xD2490 / 0x358C63` 完全一致、源码同为 `clipboard.rs:160`，
  而 memcpy 一个在 304 行、一个在 342 行——**同一处崩溃**。

## 二十六、贴图长图放大"图片不放大、只边框在放大"：系统跟踪尺寸收口（2026-10-24）

**现象**（用户原话）：*"贴图，长图，放大之后，图片并没有放大，只是外部的边框在放大。
可以试着复制很多行文字再贴图。"* 复现口径：*"对于宽高比极端的图，我进行放大，实际上图片
没有真的放大。因为多行短文字就会变成特别长的图，一下就能看出来。"*

**根因**：**两个各自独立的原因叠在同一个现象上**，第二根是这次新查出来的。

1. 布局陈旧（早已修）：贴图窗被 `on_wheel` 用 `SetWindowPos` **外部**缩放，windui 的
   `WM_SIZE` 只重设后端缓冲、不请求重排 ⇒ `paint` 拿到的 `bounds` 停在 100% 旧尺寸。
   `live_bounds` 改拿 `GetWindowRect` 真尺寸作画治这条。
2. **系统跟踪尺寸收口**（本次）：固定大小 + `frameless` 的窗样式仍是
   `WS_OVERLAPPEDWINDOW & !(WS_THICKFRAME|WS_MAXIMIZEBOX)` 一族，`CreateWindowExW` 与
   `SetWindowPos` 都按 `WM_GETMINMAXINFO` 的跟踪尺寸收口——**宽硬下限
   `SM_CXMINTRACK`（本机 136）**、**高上限约一屏（本机 1100）**。
   - 窄长条图（多行短文字栅格化的 60×720，12:1）窗口被顶到 136 宽 ⇒ `fit_aspect` 把图
     居中、两侧各 38px 黑边；
   - 长图放大到窗高越过 1100 后**图片高度被钉死**，而窗口另一维还在按百分比长 ⇒ 图片
     尺寸冻结、外框继续变大——**用户看到的就是这个**。

**探法定根因**（`tests/probes/pin_zoom_clamp_probe.rs`，四变体对照）：

| 变体 | 做法 | 结果 |
|---|---|---|
| 0 | 默认（`DefWindowProcW`） | 要 64×724 → 136×724；要 64×3004 → 136×1100 ★被钳 |
| 1 | 接管 `WM_GETMINMAXINFO`，min=200 / max=16384 | 要 64×724 → 200×724（min 生效、高不再钳） |
| 2 | **只写 min=(1,1)**，不碰 max、不调 `DefWindowProcW` | 与变体 0 **完全一致**，仍被钳 |
| 3 | 建窗后换样式 `WS_POPUP` | 2×80 / 3000×80 / 60×4000 **全部原样授予** |

变体 2 是**专门为排掉一个很自然的猜测**加的：`Window::min_size(1,1)` 正是"只写
`ptMinTrackSize`、`min_w>0` 时提前 return 不写 max"——实测它**一点用都没有**（136 是
Windows 对非 popup 样式的硬下限，`ptMinTrackSize` 写 1 也压不到更低）。不测这一下就会
顺着 `.min_size()` 往下走，白绕一圈。

**修法**：windui 补丁 095 新增 `Window::popup(on)`，`create_window` 里
`if cfg.popup { win_style = WS_POPUP; }`；主仓 `pin.rs::open()` 加 `.popup(true)`。
选"建窗即对"而不是"建窗后再换样式"：后者还得把 `CreateWindowExW` 当场收口掉的尺寸
重新要一次，且那一下不能在 `paint` 里做（`SetWindowPos` 同步派发 `WM_SIZE` ⇒ 重入
`state.paint` ⇒ `&mut` 别名 UB），要么挂常驻定时器、要么等第一次输入，都有可见代价。

**换了样式，frameless 其余机制不受影响**（三者都不看样式位）：`WM_NCCALCSIZE` 读宿主
状态；`WM_NCHITTEST` 的缩放热区判据是 `WS_THICKFRAME`（新旧样式都没有它）；本窗
`min_w/min_h` 恒 0，`WM_GETMINMAXINFO` 落到 `DefWindowProcW` 时 popup 无收口。

**验收**：`pin_zoom_e2e_probe`（真 exe + 剪贴板放 60×720 纯品红 CF_DIB + `SendInput` 发
Ctrl+Alt+P + 截屏量品红包围盒）：
- 修后：`style=0x94000000`，出厂窗口 **64×724 == 图 + 2×FRAME**，客户区 == 外框，品红
  包围盒 **(2,2,60,720) 铺满无黑边**；滚 3 格后窗 82×940、品红 (2,2,78,936)，**都 ×1.30**。
- **判据自己红一次**：临时撤掉 `.popup(true)` 重跑 → 出厂断言当场报"要 64x724，实际
  136x724、style=0x14c80000"，与用户报的现象逐位一致。

- ★ 教训一：**"算式对"不等于"算式落到窗口上"**。`frame_inflate(zoomed_size(...))` 一直
  算得对，单测也一直是绿的——病在中间那一层（OS 收口）。所以几何不变式要**两头钉**：
  单测钉算式、真机探针钉"算式真的落到窗口上"。
- ★ 教训二：**候选修法要一个个排掉，别停在第一个像的**。这次"`ptMinTrackSize` 压不下去"
  和"`ptMaxTrackSize` 默认就够小"是两件事，只有四变体对照能把它们分开；少了变体 2，
   `.min_size()` 这个错误方向看着完全合理。
- ★ 教训三：**探针必须自检前置条件，而且要在"最后一刻"自检**。第一版 e2e 探针没查剪贴板，
  恰好撞上残留文本（`read_clipboard_content` 文本优先），贴出来一张 449×45 的文字栅格，
  尺寸断言报"要 64×724 实际 453×49"——红得很像缩放 bug，其实前置条件就没成立。补上检查后
  又红过一次：起进程前查是干净的，3 秒后却被写进了文本（本机装着 Quicker 等剪贴板工具，
  未逐一定位是谁）。现在探针的做法是**起进程后轮询打印（诊断）+ 按快捷键前一刻重放图并
  复验（保证）**——只查一次不重放，探针就会时红时绿，那样的判据等于没有判据。
- ★ 教训四：**`SendInput` 注入的滚轮事件偶发整条丢失**（实测 3 格里丢过 1 格，探针报
  "只长了 2 格"的假红）。判据是"窗高有没有变"（单调递增），变了就是生效了；每格重试到生效
  为止。★ 分辨"注入丢事件"与"应用脱层"（`pct` 改了却没改尺寸）的办法是看**增量**：
  重试后一次长 10% = 注入丢的；一次跳 20% = 应用侧早退造成的脱层，那才是真 bug。
  本次实测重试全部救得回来 ⇒ 是注入侧，应用无责。
