## 0. 总原则

1. **先公约数，后功能**：任何新功能先问"落在哪一层"，不允许私开底层设施。
2. **克制引库**：纯 win32 + windui + Lua；引第三方库需给出体积/维护代价论证（前例：nnnoiseless = 纯 Rust 移植、零 C 依赖，走 crates.io——2026-09-28 从 vendor 改回，确认无补丁后没必要多养一份本地源码；gifski 因体积翻倍 → 不引）。
3. **每个覆层窗必须登记捕获可见性策略**，这是所有"自己录自己"问题的总闸。
4. **扩展优先 Lua 目录**：绘制类效果 = 脚本文件，不重编译。
5. **改完必过门禁**，但"过"不等于"全量重跑"——**编译是唯一的大头**：测试本身只跑几秒，
   改一个 `.rs` 重新编译却要约 1m25s。按需检验请用
   `python main/build/gate.py <组名…>`（见《踩坑记录》§1.2）。

## 2. 公约数分层架构

```
① 输入钩子层     鼠标移动/点击 · 键盘 · 快捷键            → 1 3 4 9 14
② Lua 特效契约   effect_name+schema+init/on_move/step/draw → 1 2 3 14
③ 覆层宿主层     透明窗 · Backdrop{Frozen,Veiled} · CapturePolicy · 覆层栈 → 5 6 11 12 13 15
④ 捕获层         ScreenSource{ oneshot=GDI, stream=DXGI } → 6 7 8 12
⑤ 编码层         MF SinkWriter(H264/MP4) + 序列帧→GIF    → 7 8
⑥ 全局服务       WASAPI · 墙钟计时状态机                              → 4 15
⑦ 独立复合件     虚拟键盘（输入钩子+覆层绘制+布局脚本）    → 10
```

已有：①②④(两套并存)⑤⑥。缺口：③ 的 CapturePolicy 与覆层栈、④ 的统一接口（见 §3）。

> **2026-09-26 状态核对**：③ 只落地了**一半** —— `WDA_EXCLUDEFROMCAPTURE`（每张该排除的
> 独立窗自己声明）已用起来（`platform/pip_window.rs`），但 §3.2 的
> **Capture Broker（单例 DXGI 会话 + 帧分发）至今没有实现**，录屏与 GIF 各自持有独立的
> DXGI 会话。③ 的"覆层栈 + 模式仲裁"与 ④ 的统一接口同样**未落地**——

## 3. 功能打架的根治（底层，非工具栏）

### 3.1 核心问题：捕获会话竞争

用户明确指出：如果 GIF、录屏、局部放大各开一个 D3D11 设备 + 各自的 DXGI
Duplication 会话，将导致——

- **资源浪费**：两份 GPU 纹理、两套帧缓冲，内存翻倍；
- **会话冲突**：DXGI Desktop Duplication **同一时刻全进程只容一份**——旧的还活着时
  再 `DuplicateOutput` 恒得 `0x80070057`，**换一台新 D3D 设备也一样失败**
  （实测：同设备 ✗ / 换设备 ✗ / 先释放旧的 ✓，见
  `tests/probes/capture_smoke.rs::a_second_duplication_needs_the_old_one_released`）；
- 两个会话竞争同一显示器时行为不可预期。

**结论：工具栏/模式互斥解决不了这个，必须在底层做单例。**

### 3.2 方案：捕获经纪（Capture Broker，单例服务）

```
                 ┌─ 消费者A：录屏编码（MF SinkWriter）
每个显示器一个     │
DXGI 复制会话 ──→ Broker 帧分发 ─┼─ 消费者B：GIF 序列帧采集
(唯一 D3D11 设备) │             │
                 └─ 消费者C：局部放大/放大镜（读回区域纹理）
```

设计要点：

1. **platform 层新增 `capture_broker`**：全局单例，持有唯一的 D3D11 设备 +
   每显示器一个 `IDXGIOutputDuplication` 会话（懒创建、引用计数、最后一个消费者退出时释放）。
2. **消费者模型**：消费者注册回调（或帧队列 Sender），Broker 在 AcquireNextFrame
   后把纹理**拷贝**（`CopyResource`）分发给各消费者——消费者之间零共享可变状态。
3. **节拍仲裁**：取所有活跃消费者的最高帧率为采集节拍；无消费者时会话休眠（省 GPU）。
4. **现有 recorder.rs 改造**：把"设备+会话+主循环抓帧"拆出，录屏退化为 Broker 的一个消费者。
5. **oneshot（截图）不走 Broker**：GDI 一次性抓图无会话概念，维持独立（§1 #6）。
6. 多显卡笔记本注意：Duplication 会话必须开在拥有该输出的适配器上（枚举 DXGI
   Factory 时按输出选适配器，不是取第一块）。

### 3.4 录屏 × 放大镜：录制合成通道（2026-09-28 定稿）

画中画 / 全屏放大窗靠 `WDA_EXCLUDEFROMCAPTURE` 把自己从一切抓屏里摘掉（否则源图
抓到自己 → 无限套娃）。该标志是**系统级**的：GDI 与 DXGI 桌面复制一视同仁，于是
录屏里放大窗被整体抠掉——视频显示的是窗口底下的画面，观众看不到任何放大效果。

**为什么不录制期间动态关掉排除标志**：`SetWindowDisplayAffinity` 是窗口级开关，
没有「只对某次捕获生效」的粒度；关掉后面板对录屏可见的同时，放大镜自己的源图
抓取（GDI，30 FPS）也抓得到自己——套娃立刻回归。被遮挡的真实屏幕内容在物理上
不存在于任何捕获里，「对自家录屏可见 + 源图无递归 + 源图实时」三者在窗口方案下
不可兼得。

**定稿方案：管线合成**（`platform::capture_share`）——排除标志保持常开，让录制
管线主动来取面板画面：

```
PipWindow::present ──发布面板位图──▶ 共享槽 ──▶ Session::pump 每帧贴进采集纹理
   （屏幕上照常显示）                             （光标画在面板之上，与屏幕层序一致）
```

- 面板像素本来就是「干净源图拉伸后的结果」，贴进录制帧 = 视频里得到与屏幕一致的
  放大画面，源图通道不动、永不套娃。
- GIF 与 MP4 共用 `Session::pump`，一处合成两边生效。
- 发布只在录制会话存活期间进行（`Session::open` 开、`Session::drop` 关并清槽）；
  不录制时 `present` 零拷贝。面板跨屏 / 落在裁剪区外时按矩形求交自动跳过。

### 3.5 常驻内存策略：两段式瘦身（2026-09-28 定稿）

参考 pecia（`.ex/pecia`，C++ Markdown 编辑器）markdown 预览关闭时的做法，把"轻量"拆成
两段：**真释放**让内存确实可回收，**工作集裁剪**让任务管理器的数字回落——后者不释放
任何内存，只是把释放后的空闲页摘出工作集交还系统，但常驻软件的"内存大不大"观感恰恰
由它决定。

- **第一段（真释放，早就位）**：功能开关的**边沿**上 `release_memory`（拖尾/回显/
  键盘/标注各自归还独占资源，见 `Runtime::reclaim_disabled_modules`——只在边沿做，
  逐帧回收会把刚加载的用户图片立刻丢掉，优化变劣化）；录制缓冲随 `Session::drop`；
  面板状态随 `close_panel` 的 `take()`。
- **第二段（工作集裁剪，`platform::working_set`）**：上述低频重事件后**延迟 2 秒**
  调 `EmptyWorkingSet(GetCurrentProcess())`。三条纪律（pecia 踩过的坑直接继承）：
  只事件驱动、不做 idle/定时轮询；延迟 2 秒等页进 standby；录制进行中不裁
  （录制缓冲是最大常驻块，逐出后每帧采集都缺页，"切回来变卡"）。重复请求在延迟
  线程里按代数合并。

### 3.6 裁剪窗（GIF / 视频）的外壳、预览与保存（2026-09-30 定稿）

**定稿：留系统标题栏 + 可缩放**（`runtime::layer::gif_trim` / `mp4_trim` 两窗一致）。

- 无边框只对"内容就是窗口本身"的窗（覆盖层、选框、贴图）成立；裁剪器是**工具窗**，该有的
  最小化 / 最大化 / 边框都得有。
- 布局的唯一依据 = **当前客户区尺寸**：预览吃满"扣掉摘要 / 轨道 / 刻度 / 按钮之后的
  剩余高度"（下限 `PREVIEW_MIN_H`），窗口拉大即画面变大；`min_size` 兜住下限。
  ★ 顶部不留页眉——提示行删掉后留白也一并删（2026-09-30 追加定稿）。
- **标题栏 = "文档名 - 软件名"**（与记事本同一套口径，`window_title`）：任务栏 / Alt-Tab 里
  先看到用户自己那份文件。★ 标题是**动态**的，而 `FindWindowW` 只认完整标题 —— 模块自己
  记一份当前标题（`cur_title()`），所有按标题的关窗 / 聚焦 / 重画都走它；活窗在 `paint` 里
  每帧校准一次（`.single()` 让重复触发不重建窗，那条路会把这份记录写歪）。
- **内容区零提示**（2026-09-30 用户定稿"标题栏有了就行"；同日追加：页眉整行删除，删了
  内容就不留白）：**报错红色顶替摘要行显示**，空窗预览是纯深底、不写说明，摘要行只在
  载入后出现；窗口名里直接带格式——视频窗叫
  **"CurSeen MP4 裁剪"**（管线与文件对话框都只收 `.mp4`），GIF 窗叫"CurSeen 裁剪 GIF"。
  不设「取消」按钮：标题栏 ✕ / Esc 即取消。
- **刻度（"0.0s / 总长"）独立成行**（`TICK_H`），与按钮之间留整 `GAP` —— 它原本画在轨道
  命中框末尾，16px 高的字会压到按钮上。
- 预览时刻按 **100ms 量化**：同一格内不重复解码（一次几十毫秒，拖动才不涩）。
- **保存：另存为对话框在 UI 线程，写盘在工作线程**（`SaveState` + `on_interval` 收尾），
  轨道位置改画进度条、按钮全灰。视频侧必须显式关掉 SinkWriter 节流（见
  `platform::mp4_trim` 模块头与《踩坑记录》§9.3），否则 13s 的片子要写 155s。
- 两窗**刻意不共享代码**：GIF 那份带满测试，抽公共组件要连测试一起翻新，风险大于重复；
  第三个裁剪器出现再抽。★ **改一处记得改另一处**（GIF 侧是进程内重写 GIF，毫秒级，
  仍在 UI 线程同步跑）。

## 4. Lua 脚本跨模块复用（拖尾/波纹/悬浮标/激光笔）

### 4.1 现状与目标

三者已是同一契约（`effect_name`+`schema()`+`init/on_move/step/draw`），但目录按
模块隔离（`assets/lua/MouseTrail/`、`assets/lua/ClickFx/`…；★ 这是**统一 Lua 脚本根
`assets/lua/` 之下**的子目录，不是 `assets/` 直接子级）。目标：

1. **脚本文件即能力**：一个脚本放进哪个模块目录，就在哪个模块生效；复制文件即可跨模块
   （激光笔.lua 放进悬浮标目录即可与其共存，放进拖尾目录可与拖尾共存）。
2. **同一脚本多模块启用天然共存**：用户可"激光笔+悬浮标"或"激光笔+拖尾"同时开，
   各模块各自实例化、各自渲染，互不知晓。
3. 实现上：模块→目录的映射保持现状（目录即来源），只需保证**绘制不互相清屏**（并集
   渲染已用一条自交多边形 + Winding 规则，满足）。

### 4.2 激光笔方案（#14 定稿）

- **形态**：一个 Lua 脚本——隐藏指针（schema 声明 `hide_cursor=true`），无拖尾，
  每帧在指针位置画一个实心圆（颜色/半径/描边可配，进 schema）。
- **放置**：出厂放「悬浮标」模块目录；用户可复制到拖尾/波纹目录自由组合。
- **不做成独立功能开关**：它就是一个特效脚本，进各模块的启用列表即可。

### 4.3 `scripts/` 独立脚本的边界：启用开关 / 热键 / 实例（2026-09-30 定稿）

`scripts/` 下每张卡片标题栏的开关就是它的**启停用**（`LuaExtSettings::set_role_active`，
判定只有 `role_is_active` 一个入口）。三条由此派生的契约：

1. **热键必须先过开关**：卡片参数里的 `hotkey` 与启用列表是两条独立持久化链路，
   `Runtime::script_hotkeys` 在派生名单时就用启用列表过滤；这份名单同时喂
   `handle_action_key`（派发）与 `action_hotkey_wakes`（park 唤醒）——一份名单两处消费，
   不会出现"开关关着还能把休眠的覆盖层叫醒"。命中但没启用 = 忽略 + 一行 warn。
2. **同一脚本同时只跑一个**：去重做在派发器（`ext_runner::try_claim` 进程级登记表）而不是
   具体窗口里——`run_ext_detached` 每次新线程，窗口侧的线程局部状态压根看不见别的线程。
   ★ 这条是通用的：`ext:chat_window` / `ext:result` / `ext:input` 一并受益。若某个窗口还要
   "叫回来而不是再开"，取进程级句柄做判据（**不要按标题**——标题会随状态变）。
3. **Lua 回调一律可选**：一次性 / 开窗脚本（只有 `schema` + `run`，如 AI 写脚本）勾了开关也会被
   当常驻实例逐帧分发；缺 `init` / `on_move` / `step` 是"它不关心"，必须静默跳过，不得告警
   （`draw` / `on_press` / `on_mouse_down` 早已是这个口径）。

## 5. 虚拟键盘可定制方案（#10 定稿，v2 依据开源源码精读修订）

> v1 结论是"layout.lua 布局脚本"。精读 `.ex/按键显示与虚拟键盘` 26 个项目后修订：
> **布局是数据不是逻辑，主格式改用 JSON（对齐同类主播键盘生态），Lua 仅留作可选行为扩展。**

### 5.1 源码证据（同类主播定制键盘生态的事实标准实现）

- **目录即来源**：社区通行 `keyboards/<作者>/<方案>/keyboard.json`，已有海量现成方案
  （游戏 FPS / Dota / 魔兽 / 鼠标组合布局……），正是"WASD 主播键位"需求的成熟生态。
- **元素多态**：`Elements[].__type` 不止键盘键——还有 `MouseKey`（鼠标按键上屏）、
  `MouseScroll`（滚轮）、`MouseSpeedIndicator`（移速指示）。主播布局里鼠标和键盘同屏是刚需。
- **任意多边形键帽**：`Boundaries` 是顶点列表而非矩形 → 键帽形状完全自由（异形、贴边、
  圆角框选区），天然映射到我们 windui 的多边形 DrawCmd 能力。
- **一键多绑**：`KeyCodes: List<int>`——一个键帽可同时绑定多个 VK（如宏展示），
  一个 VK 也可被多个键帽共享（如左右 Shift 分开画）。
- **大小写/Shift 文本**：`Text` / `ShiftText` / `ChangeOnCaps` 字段齐全。
- **反例（标杆实现没有）**：它纯展示、无 SendInput 交互；交互要自己补
  （另有少量同类项目有发送实现可参考）。
- **其余实现**：有的把布局硬编码在应用代码里（不可文件定制，反面教材）；
  用 SVG 表达布局的（表达力强但解析重）；脚本系实现为玩具，不足为训。

### 5.2 选型（v2 定稿）

| 方案 | 结论 | 理由 |
|------|------|------|
| **JSON 布局文件（主格式）** | ✅ | 布局是静态数据，JSON 声明式、可工具化（将来面板内做布局编辑器）、无脚本注入面 |
| Lua（可选行为钩子） | ✅ 叠加 | 仅 `on_key(code,down)` 一类动态行为需要；90% 方案用不到 |
| C DLL | ❌ | ABI/安全/编译门槛（维持 v1 结论） |

> ★ **"吃同类生态存量"这条只在设计阶段成立**：代码里**没有外部方案导入器**
> （2026-09-24 工作区清理时随一次性脚本一起移除）。我们的格式是**平铺单文件**（§5.3），
> 与社区通行的 `keyboards/<作者>/<方案>/keyboard.json` 多边形格式不同构，**不能**直接导入——
> 拿来的方案要手改成我们的行数组格式。别再据此对外承诺"兼容社区方案"。

### 5.3 方案设计（v2）

- **目录**：`assets/VirtualKeyboards/<方案 id>.json`（**平铺单文件**；每个文件一套方案，
  不再有子目录形态）。
- **★ 目录即来源（2.x 已落地）**：程序里**没有"方案白名单"** —— 启动时扫描该目录，**目录里
  的每个 `.json` 就是一套方案，文件名（不含扩展名）即方案 id**，「虚拟键盘」卡的下拉按
  **文件名**排序列出。**用户丢一个 `.json` 进去、能解析，方案立刻可用**：不必改配置、不必
  重启、不必重编译。
  ★ 早期设计是「每个含 `keyboard.json` 的子目录一套方案」（对齐同类社区生态），
  **已改为平铺单文件**：`ansi_104/keyboard.json` 那种 nested 形态不再存在，想跟着教程放
  子目录只会变成"多出一套读不出几何的空方案"。
  出厂四套同时以 `include_str!` 内嵌进二进制（`layout::BUILTIN`）：
  `ansi_104` / `ansi_104_dark`（双色）/ `ansi_60` / `wasd_gaming`（游戏 WASD + 鼠标）。
  —— 目录被清空或误删时仍有键盘可显示（不至于白屏），目录里有同名 id 的方案时以目录那份为准。
- **★ 单文件自包含**：一个方案 `.json` 同时决定**几何**（`rows` 行数组 + 每键 `w/h/pad`）、
  **逐键文字**（`text` / `shift_text`）、**默认值**（`defaults`）、**配色**（`styles` /
  `state_styles` / 逐键 `style`）——**分发单元就是一个文件**，拷给谁都能完整还原。
  `styles` 只是文件内部解耦手段（免得 104 个键重复写颜色），不是拆分文件。
- **★ 实现现状（2026-09-17 第二次校对，以代码为准）**：格式是 **"行数组 + u 单位"**，
  解析在 `modules/virtual_keyboard/layout.rs::LayoutJson`，真实字段如下：

  ```json
  {
    "name": "ANSI 104 键",
    "defaults":    { "font_size": 14, "corner_radius": 4, "scale": 1.0 },
    "styles":      { "modifier": {"fill":"#3A3F47","text":"#E8E8E8","border":"#2F343A","radius":4} },
    "state_styles": { "pressed":  {"fill":"#FFB454","text":"#1A1A1A"} },
    "keys":        { "Backspace": {"style":"modifier"} },
    "rows": [
      { "keys": [ {"code":"`","text":"`","shift_text":"~","pad":0.5}, {"code":"Esc"} ] },
      { "keys": [ {"code":"a","text":"a","shift_text":"A","caps":true} ] }
    ]
  }
  ```

  要点：
  - **`rows` 就是几何本身**，不再有"引用内置布局"这一说。只写 `base_layout`（指向内置
    方案 id）不写 `rows` 时，就是一套"纯配色方案"，几何沿用被指向的那套。
  - `code` 三种写法：单字符（`"q"` / `";"`）、枚举名（`"Esc"` / `"LShift"`）、带编号
    （`"F5"` / `"Num3"`）。解析见 `layout::parse_code`。
  - `text` = 常态图例；**`shift_text` = 按住 Shift 时键帽印的字**（省略 = 与 `text` 同）。
    "让某个键在 Shift 下显示别的名字"就写这里。
  - **字段名一律蛇形**（`shift_text` / `state_styles` / `font_size` / `base_layout`），不混
    驼峰。`shiftText` / `baseLayout` 作为**别名**仍能解析（早期手写的方案不至于忽然失效，
    且是静默失效——错键名不报错），但新写的方案请用蛇形。
  - 想给一套键盘换配色而**不重抄 104 个键位**：**不写 `rows`，只写 `base_layout`** ——
    这就是"纯样式方案"。出厂带一份活样例：
    `assets/VirtualKeyboards/ansi_104_dark.json`（**"ANSI 104 双色"** —— 键帽只分
    「输入键」与「功能键」两类，分类写在 `keys` 表每颗键的 `style` 上）。
    几何优先取**目录里**被引用的那套（用户改了 `ansi_104` 的几何，样式方案跟着变），
    目录里没有才用内嵌那份。
  - `caps: true` = 该键受 CapsLock 影响（字母键要写）。Caps 与 Shift 是**异或**关系
    （同类实现里一行公式）：字母两个都按下反而回到小写，数字/符号只看 Shift。
  - `1u` = 一个标准键的边长；非标准键全靠 `w`（Tab 1.5 / Caps 1.75 / Enter 2.25 /
    Space 6.25 / 底排修饰键 1.25）；`h: 2` = 竖着占两行（小键盘 `+` / `Enter`）；
    `pad` = 本键之前的额外留白（功能键行分组、导航区与小键盘分栏）。**不需要多边形**。
  - 优先级 **面板值 > 方案 `defaults` > 内置默认**。判据是"面板值 == 出厂默认 ⇒ 视为
    未设置"，滑块一动就压过方案（`VkConfig::load` 的文档写明了这条 unset 试探法）。
  - **图例恒为"随 Shift 切换"**（2.x 删掉了面板上那个开关：输入法都在做的事没有理由
    做成选项；要固定就写 `shift_text` 把上档名写死）。**唯一真相来源是几何里的
    `text` / `shift_text` 两层**——不要再引入第二套 shift 映射表（两处并存时布局表的
    shift 层会被旁路掉，画不出来）。
  - `keys[code]` 里的键名 = `KeyCode` 的 Rust 枚举名（`"Backspace"` / `"CharA"` / `"F5"`），
    由 `vk_config::code_to_name` 生成；可选 `text` / `shift_text` / `style` / `radius`。
  - **侧壁（2026-09-28）**：样式级 `"side"`（侧壁色，`#RRGGBBAA`）+ `"depth"`（厚度 px，
    0–12，缺省 3 但未写时为 0）——先画"下移 depth 的侧壁键帽"再画本体，底边露出一圈
    即键帽厚度；**按下时本体下移坐进侧壁**（真键帽的按压物理感）。一个特性同时参数化
    "硬阴影"键帽（暗色侧壁/白反光侧壁）与"双层"键帽（侧壁=裙边色、
    按下色=裙边色 → 顶面沉入露裙边）。没写 `side` 的样式与旧版渲染逐字节一致。
    侧壁色/厚度在面板「颜色/数值」组有对应控件（`styles.<n>.side` / `.depth`）。
  - **出厂方案**在 `assets/VirtualKeyboards/`：行方案 `ansi_104.json` / `ansi_60.json`
    （由旧 Rust 常量表一次性导出，逐键校验过），样式方案 `ansi_104_dark.json`（双色）、
    `wasd_gaming.json`（游戏 WASD+鼠标，2026-09-26），以及四套外来样式移植
    `ansi_104_kiosk_dark.json`（硬阴影键帽·暗夜）/ `ansi_104_kb_double.json`（双层键帽·Dracula）/
    `ansi_104_zh_light.json`（轻立体·晨白）/ `ansi_104_vhand_dark.json`（终端·荧光，
    2026-09-28）。其中 `ansi_104` / `ansi_60` / `ansi_104_dark` / `wasd_gaming` 四套
    同时 `include_str!` 内嵌进二进制作兜底；四套外来样式只随 assets 分发（样式素材，
    不承担兜底职责）。

- **二期目标格式（尚未实现，方向不变）**：`elements` 独立几何 + `poly` 任意多边形键帽 +
  `codes` 数组一键多绑 + `type ∈ {key, mouseKey, mouseScroll, text, image, sprite}`。
  届时的样例（**当前代码不认这个格式**，别照抄进 assets）：

  ```json
  {
    "name": "WASD-Streamer", "width": 300, "height": 200, "version": 1,
    "params": { "theme": "dark", "scale": 1.0, "opacity": 0.85, "interactive": false },
    "elements": [
      { "type": "key", "codes": [87], "poly": [[10,10],[70,10],[70,70],[10,70]],
        "text": "W", "shift_text": "", "style": "primary" },
      { "type": "mouseKey", "codes": ["L"], "poly": [/*…*/] },
      { "type": "text", "at": [150, 20], "value": "键位演示" },
      { "type": "image", "at": [/*…*/], "file": "logo.png" }
    ]
  }
  ```
  它有两条前置：几何模型要从"行数组 + u 单位"换成"多边形集合"（`layout.rs` 重写），
  命中检测要从矩形换 `PtInRegion`。做之前先评估这份收益（任意形状键帽 / 一键多绑）
  是否值这个代价。

- **样式层（形状/颜色定制，JSON 足够）**——键帽不写死颜色，引用样式名（CSS 思路），
  字段名按实现（下划线风格，不是驼峰）：
  ```json
  "styles":       { "modifier": {"fill":"#3A3F47","text":"#E8E8E8","border":"#2F343A","radius":4},
                    "primary":  {"fill":"#1F6FEB","text":"#FFFFFF","radius":8} },
  "state_styles": { "pressed":  {"fill":"#FFB454","text":"#1A1A1A"} }
  ```
  四级覆盖优先级：**内置默认 → 方案级 `styles` → 单键 `keys[code]` → 面板实时值（最高）**。
  - 状态集目前只有 `pressed`（`state_styles` 目前只读这一项）；`idle/disabled` 是二期待补；
  - 静态视觉（颜色/圆角/边框）100% 归 JSON；随时间变化的动画视觉（呼吸灯、扩散波）
    落 hook.lua——复杂度守恒，两边都不高；
  - 出厂内置主题四套（`assets/VirtualKeyboards/` 下的 `ansi_104.json` / `ansi_104_dark.json`
    / `ansi_60.json` / `wasd_gaming.json`）；"换主题" = 在「虚拟键盘」卡的下拉里换一套方案
    （★ 就是换一个 `.json` 文件，不是换一层目录）。
- **★ 面板控件 = 方案声明（2026-09-17 落地）**：「键盘外观」「键盘配色」两卡的每一行
  都由方案 JSON 的 `controls` 块决定（**与 Lua 脚本暴露参数输入同一套思路**）：
  ```json
  "controls": [
    {"id":"keySize","label":"键帽大小","bind":"defaults.keySize","min":20,"max":64,"step":1},
    {"id":"primaryFill","label":"主键蓝","bind":"styles.primary.fill","type":"color"}
  ]
  ```
  - `bind` 路径：`defaults.keySize|gap|opacity|hold|fontSize|cornerRadius|scale`、
    `base.fill|press|border|text`、`pressed.fill|text`、
    `styles.<名>.fill|text|border|radius`、`keys.<键名>.radius`（解析见 `Bind::parse`）；
  - **没写 `controls` 也照样能用**：代码自动补齐预设项（六个外观项 + 四个兜底色）
    **加上**方案里出现的每个命名样式色 —— 于是"方案给某些键上了别的颜色"在面板上
    一定有对应的色块可改（这正是上一轮"看得见改不了"的坑）；
  - 声明是**覆盖不是替换**（按 `bind` 去重）：作者少写一项不会让用户少一个可调项；
  - 用户改过的值落在 `virtual_keyboard.params[方案 id][控件 id]`，只写"与方案默认不同"
    的项 —— 换方案再换回来各自的值都还在，方案改默认值用户也能立刻看到；
  - **三个窗口行为（鼠标穿透 / 总在最上 / 全屏避让）与位置偏移不开放给方案**：它们
    改的是窗口与输入行为、几何位置，让方案预设一个值只会让人猜不到当前状态。
- **泛化：方案 = "输入驱动视觉方案"（对齐"输入事件触发形象动作"类桌宠需求，源码精读 2026-09-17）**。
  该类方案（Tauri + easy-live2d 壳）本质 = 输入事件 → 触发模型部位/动作；其"键位设置"
  是纯数据映射（哪个键 → 哪个部位），与我们 codes 绑定同构。对照结论：
  - JSON 增加 `sprite` 元素类型：`{ type:"sprite", bind:[codes],
    states:{idle:"a.png", pressed:"b.png"}, at:[x,y], z:2 }`——静态精灵木偶
    （猫爪拍键 = PNG 按状态切换），单 keyboard.json + 同目录 PNG 即完整方案，
    这类桌宠的核心观感可被吃下；单文件自包含原则不破（PNG 是被引用素材，定义仍是 json）；
  - 音效反馈复用既有 Sounds 素材目录机制（目录即来源）；手柄（XInput）留待将来；
  - **Live2D 骨骼变形动画不做**：Cubism 专有 SDK 体积大、跨平台包袱，违背小而美；
    "有过程的动画"（挤压、回弹）落 hook.lua，静态换图归 JSON——与既有分工边界一致。
- **外部方案导入器**（一次性脚本，不在仓库）：把社区通行的 `keyboard.json` 多边形格式
  转成我们格式（多边形/键码/鼠标键一一对应，丢弃该格式独有的编辑器辅助字段）——**用户可直接
  取用该社区的全部现成方案**，冷启动即有几百个布局。
- **可选 `hook.lua`**：同目录下存在才加载，提供 `on_key(code, down)` /
  `on_click(code)` 高级行为（联动特效、自定义高亮规则）；缺省行为内置。
- **交互 / 不交互（2.x 已落地）**：由**虚拟键盘自己的**「鼠标穿透」开关切换
  （`virtual_keyboard.click_through`，在虚拟键盘卡里，**不是** overlay 的窗口行为）。
  ★ **出厂是勾上的**（`click_through = true`）= **展示模式**（纯显示 + 按键高亮，点击穿到
  下面的窗口，键帽点不动）。想变成**交互模式**要**手动关掉**这个勾：
  - 展示模式（勾上穿透，出厂）：点键帽不注入、点击穿透到下层。
    ★★ **穿透只管"注不注入"，不管"收不收鼠标事件"**：鼠标键帽的高亮**唯一的输入**就是
    `MouseDown/MouseUp`，它必须与"捕获点击"各有各的门——若把两者焊在一起
    （`mouse_input_needed` 只在 `enabled && !click_through` 时才算数），勾着穿透的方案里
    鼠标事件会被桥接线程整条丢弃：键盘键照常亮、**鼠标键永远不亮**（表现为"点了没反应"）。
    两件事各有各的门：`MOUSE_INPUT_NEEDED` 管全部鼠标事件（含 1000 条/秒的 `MouseMove`，
    穿透态不开），`VK_MOUSE_ARMED` 只管**低频的按下/抬起**（方案含鼠标键帽就开，不看穿透）。
  - 交互模式（关掉穿透）：**命中检测按矩形**做（键帽就是矩形，不需要 `PtInRegion`）。链路是
    `WH_MOUSE_LL` 钩子 → 命中键帽则 `return 1` **吞掉这次点击** → 事件仍照发给 UI 线程
    → `Runtime::vk_pointer_begin` 查同一块共享区确认 → `SendInput` 注入 VK。
    ★ **鼠标键帽是例外**：`MouseLeft/Right/Middle/X1/X2` **没有键盘虚拟键**
    （`to_vk_ext` 里没有它们的分支），注入必然失败。所以命中鼠标键帽时**不做注入**，
    改为直接点亮它（`VirtualKeyboardModule::note_press`）并照样吃掉这次点击 ——
    否则就是"注入失败 + 事件被吞 + 键帽不亮"三头落空。
    （出厂方案一律给穿透，就是怕直播时在覆盖层上点一下把游戏点了。）
    吞掉是为了两件事：下层窗口收不到（点个键不会顺手在别处点一下）、前台焦点不变。
  - **不用独立窗口**：键盘是画在整屏覆盖层上的一块图形。开独立窗才能"只让键盘可点"，
    但覆盖层出厂即 `WS_EX_TRANSPARENT`，钩子拦截同样能做到"局部可点、其余照常穿透"，
    且不必处理窗口 z 序/激活/DPI 三套问题。三条关键实现：
    `platform/input/hit.rs`（UI 线程发布键帽矩形快照，钩子线程 `try_read`，**绝不等待**）、
    `platform/input/inject.rs`（`SendInput`）、`platform/input/vk.rs::to_vk_ext`（含
    `KEYEVENTF_EXTENDEDKEY`：小键盘 `Enter`/`/`、`Insert`/`Home`/方向键等不标扩展位
    会变成另一颗键）。
  - **注入键回灌高亮**：靠的是"注入的按键会走 `WH_KEYBOARD_LL` 回来"，于是虚拟键盘的
    高亮、按键显示、快捷键响应**全都自动跟上**，不必为"鼠标点的键"另开一条通路。
  - **★ 卡键兜底**（`Runtime::vk_release_all`）：注入的按下是**系统级状态**，与我们的
    进程生死无关。按住虚拟键时把功能关掉、勾上穿透、或直接退出程序，都会留下一个
    永远等不到抬起的按键（表现为"Ctrl 卡住"）。三处都补了释放。
- **全屏避让（#3）**：`platform/topmost.rs::TopmostKeeper.avoid_fullscreen`，面板
  「窗口行为 → 全屏避让」，★ 出厂**取消勾选**（2026-09-20 用户口径改过，代码里
  `OverlaySettings::default().avoid_fullscreen == false`，与 `TopmostKeeper::new()`
  的出厂值同源）。★ 它门控的是**整块覆盖层**的让位判据 ——
  虚拟键盘画在覆盖层上，所以让位时键盘、拖尾、按键显示**一起**让开。要让键盘压在全屏
  应用之上（直播/录屏演示），保持**不勾**；代价是拖尾等也一起留在上面。
  与「总在最上」是一对（别把两者的作用面说反）：**「总在最上」决定"在普通窗口之上"**
  （被别的置顶应用压住时夺回置顶带），**「全屏避让」决定"前台全屏时让不让"**。
- **底层复用**：渲染走 windui（多边形 DrawCmd 现成）；键盘/鼠标事件走现有输入钩子
  （同类实现证明鼠标键是刚需，我们钩子已有）；方案扫描/参数面板沿用既有机制。
  **新底层件只有三个**：SendInput 注入、穿透（覆盖层透传）、**矩形**命中检测
  （实现在 `platform/input/hit.rs`；多边形命中检测属二期目标格式，尚未做）。

## 6.1 便签透明度：是真透明，不是"变灰"（2026-10-24 实测定案）

用户反馈「便签透明度改变时不对劲，并不是真的透明，而是有点灰色」，开发者本机看着正常。
**结论：程序没问题，是真半透明**；"发灰"是深色便签压在浅色底上的**正确合成结果**。

判据（真机探针 `tests/probes/note_translucency_probe.rs`，`python build/probe.py run note_translucency_probe`）：

| 总不透明度 | 层 alpha | 底色（纯度） | 标题栏实测 / 理论 `a*C+(1-a)*B` | 正文实测 / 理论 |
|---|---|---|---|---|
| 100% | 235 | [248,253,255]（93%） | [56,61,68] / [56,60,68] | [67,72,81] / [67,71,81] |
| 40% | 94 | [248,253,255]（93%） | [172,176,180] / [171,176,180] | [176,181,185] / [176,180,185] |

实测与理论**逐通道差 1/255**。同一条判据的分辨力：若不透明，40% 档会差 **124**（正文）/132
（标题栏）——差 1 就是"透"的铁证。判据本身也验证过会红（把理论值换成"假设不透明"即失败）。

**为什么会看着发灰**：出厂便签色是低饱和深色（背景 `#282C34`、编辑区 `#343842`）。
40% 时层 alpha 只有 94/255 ≈ 0.37，即 **63% 是底色透上来的**——压在浅色桌面/浏览器上时，
合成结果是 [176,181,185] 这种**中性灰**，便签自己的蓝味被冲掉了。

**为什么两台机器观感不同**（这就是"你看着正常"的原因）：

| 便签背后的底色 | 40% 不透明度下的观感 | 实测（探针扫到的位置） |
|---|---|---|
| 浅色（白 / 亮壁纸 / 文档） | **发灰**——正是用户报的现象 | 正文 [176,181,185] |
| 深色（暗壁纸 / 深色窗口） | 仍是深色，看着"正常" | 正文 [19,21,24] |

→ 用户侧答复口径：**它在真的变透明，只是您背后是浅色的，深色便签半透后就成了灰色。**
   想要"看着还是便签、只是透"，有两个方向（均未实现，属需求不是缺陷）：
   ① 把便签背景色调浅/调饱和；② 上毛玻璃（亚克力）效果——透的是模糊后的底色，
   颜色不会被冲成灰。

## 9. 性能与资源占用（低内存 / 低 CPU 的设计与实测）

> 2026-09-29 补充。结论：本项目的运行时资源占用**已经是刻意压低的**——核心机制是「空闲即
> 停帧 + 关功能即释放 + 工作集整理」。下面先列**已经做对的**，再列**仍值得做的 targeted 优化**
> （按 ROI 排序），避免重造已有轮子。所有结论基于 `src/runtime/`、`src/core/draw.rs`、
> `src/modules/trail/sample.rs`、`src/runtime/mod.rs`、`src/platform/working_set.rs`、
> `src/scripting/runtime.rs`、`src/modules/trail/clickfx.rs`、`src/platform/clipboard_history.rs`
> 的实地核查。

### 9.1 已经做对的（不要再重造）

1. **Park 状态彻底停渲染**：`overlay.rs` 的 `want_park = !input_needs_frame()`，park 时
   `set_overlay_parked(true)`，平台**不再回调 `paint()`**（`overlay.rs` 注释明确「park 态下
   paint() 不被调用 → frame() 不执行」）。这是低 CPU 的基石——静止时渲染开销为 0。
2. **唤醒是事件驱动**：快捷键 / 配置变更 / 进入截图编辑态会主动 `set_overlay_parked(false)`，
   不依赖轮询出帧（修过 park 下快捷键延迟 0.6–1.2s 的问题）。
3. **每帧零重新分配**：`core/draw.rs::DrawList::clear()` 对各 `Vec` 调 `.clear()` 但**保留
   容量**；位图以 `Rc<RgbaBitmap>` 共享，绘制不拷贝像素。
4. **拖尾零分配环形缓冲**：`modules/trail/sample.rs::SampleQueue`（`CAP = 1024`）固定容量、
   覆盖最旧、迭代器不拷贝——无无界增长、无每帧分配。
5. **关功能即释放（边沿触发）**：`runtime/mod.rs::reclaim_disabled_modules()` 仅在
   off→on→off 的下降沿对 trail/key/vk/drawing 调 `release_memory()``，并 `request_trim_soon()`。
   放大镜用 `Option<PipMagnifier>` / `Option<FullscreenMagnifier>` 按配置 `take()`，关即释放。
6. **Backdrop 精确区分**：屏幕标注 = `Backdrop::None`（透明帘，**不抓屏、零位图**）；白板 /
   截图编辑 = `Frozen`（~8MB@1080p / ~33MB@4K），关闭时 `release_memory()` 把 backdrop 置
   `None` 并 `history.shrink_to_fit()`。
7. **工作集整理**：`platform/working_set.rs::trim_working_set` 在关功能后 ~2s 调
   `EmptyWorkingSet`，把空闲页交还系统，**降低任务管理器可见的"内存"数字**（录制进行中跳过）。
8. **剪贴板历史大文本落盘**：文本 ≤ 100KB 时直接进内存条目；**超限**全文写到
   `temp/clipboard/texts/<内容哈希>.txt`，条目只留 400 字节预览（按字符边界截断），
   粘贴/复制时从盘上读全文（`clipboard_history.rs`，2026-09-29 用户口径："超出限制的
   文本直接作为文件存入"）。缩略图 ≤ `THUMB_MAX_W = 720`；贴图环有 `pin_ring_cap` 上限。
9. **VM 稳态受约束**：`scripting/runtime.rs::EngineCache` 按脚本路径缓存长期 VM，按
   `(mtime, len)` 热重载并 `gc()` 清理已删脚本；`FxCore` 实例常驻而非每帧重建。

### 9.2 仍值得做的 targeted 优化（按 ROI 排序）

1. **点击特效 VM 池化（高 ROI / 中风险）**：`modules/trail/clickfx.rs` 每次鼠标按下若启用
   脚本化点击特效，就 `FxCore::load` 一个**全新 Lua VM**（`CLICKFX_CAP = 64`、
   `MAX_AGE_S = 8s` 老化清理）。快速连点会反复构造/丢弃 VM（每个数百 KB~数 MB），存在瞬时
   尖峰。建议按脚本 id 缓存常驻实例、复用 `FxCore` 的热重载机制，复用而非每次 `new`。
2. ~~剪贴板历史「不限」档加硬上限~~ **已否决**（2026-09-29 用户口径："要允许真无限"）：
   曾在 `evict()` 加过 10_000 硬上限安全网，按该口径拆除。内存责任转移给用户——单条
   有界（100KB / 720px）仍在，总条数不再设防。
3. **（可选）park 时停两个常驻定时器 + 释放 4K backbuffer（极小 ROI / 中风险）**：
   `PANEL_POLL`(250ms) / `MOUSE_POLL`(33ms) 在 park 时仍唤醒，但其回调是幂等短路 + 极廉价
   syscall（如 `poll_clipboard` 仅一次 `GetClipboardSequenceNumber` 比对），开销可忽略；
   仅在极端省电 / 4K 多屏大用户场景，才值得在 `set_overlay_parked(true)` 时 `cancel_interval`
   并在 unpark 重建、或释放分层窗 backbuffer（@1080p ~24MB / @4K ~100MB 常驻）。

### 9.3 设计判据（给后来的优化）

- **「空闲 = 0 功耗」优先于「功能随手可用」**：任何新增逐帧逻辑都必须能进入 park / 靠
  `draw` 是否还在画来判活；不得在 idle 时维持定时器出帧。
- **关闭即释放优先于「留着下次快」**：模块 / 缓冲 / 冻结帧在 off 的下降沿回收，靠
  `EmptyWorkingSet` 压低常驻观感，而不是常驻一堆用不上的资源。
- **分配复用优先于「每帧 clear」**：固定容量环形缓冲、`Vec::clear()` 保容量、`Rc` 共享位图。
- **单条有界优先于「总数不限」**：任何会随运行时间累加的容器都要有**单条**上限；
  总数是否设硬顶由用户裁决（剪贴板「不限」= 真无限，2026-09-29）。

## 10. 体积优化策略（方法、实测与终点）

> 2026-10-08 收口。回答「exe 还能不能更小」：**6.61 MB ≈ 当前架构下限，体积优化已收口**。
> 本节沉淀方法论与实测证据——后来者想再抠体积，先按 §10.3 的流程**重测**（要数字就现场
> 跑一遍，别信旧数字），再用判据决策，不要凭直觉动手。

### 10.1 基线构成（2026-10-08 实测）

exe 6.61 MB 的 PE 节表：**.text 5.22 MB（79%，机器码，唯一可挤的战场）**；
.rdata 1.47 MB（22%，字符串字面量 / 常量 / vtable——代码层重构碰不到）；
.pdata 208 KB（异常展开表，与函数个数成正比）；其余 ~40 KB（资源 / 重定位）。
解析方法：Python 读 PE 节表即可（读 `e_lfanew` → 节表，无需 dumpbin），几分钟可复现。

### 10.2 已落地的收益（按收益排序）

1. **`native-tls`（Schannel）替换 `rustls`+`ring`**：7.51 → 6.61 MB（−921.5 KB，−12.0%），
   单项最大。配置与三个坑见 `Cargo.toml` `ureq` 条目注释与《踩坑记录-4》§十九。
2. **`opt-level = "z"` + 仅渲染内核单包提到 3**：见 `Cargo.toml` `[profile.release]` 注释
   （全局 3 = +2.31 MB / +30.7%，已否决；台阶式无中间档，全局 2 ≈ 4.55 MB 与 3 相差无几）。

### 10.3 再优化的决策流程（先测后动，止损优先）

1. **跑榜单**：`cargo llvm-lines --release --lib`（包内多 target **必须加 `--lib`**，
   否则 rustc 报 extra arguments）。工具：`cargo install cargo-llvm-lines`。榜单留
   `temp/llvm-lines-report.txt`。
2. **判据**（2026-10-08 实测，三条全部触发「不做」）：
   - 单态化重复：copies>1 的函数 = **0 个** ⇒ 「深泛型展开多份」在本库不存在，去泛型整改无靶子；
   - 集中度：前 100 大函数仅占 IR **11%** 且全是真实业务逻辑（serde 派生 / 页面构建 / 录屏）⇒
     无「改几处省几百 KB」的热点；
   - 结论：整改收益撑死几十 KB，几天工作量 + 全量回归不成立 ⇒ **止损**。
3. **红线**（未来真要动代码省体积时）：热路径（光栅化 / 帧循环）禁改 `dyn`——单态化
   在那里是性能必需；改完代码变扭的点不做（宁可少省）；动手前 `.bf` 快照，收工 1183 测试全绿。
4. **已评估否决的路**：PGO（`opt-level="z"` 卡死内联，PGO 红利吃不到大半，两段式构建
   负担重）；编译提速三件套（`[profile.fast]` 等，不影响成品 exe，属开发体验另议）。
5. `.rdata` 1.47 MB 的其它刀（精简 panic / 格式化字符串、`trim-paths`）不在本策略范围，
   需要时另行立项评估。

### 10.4 一句话结论

体积优化的正确姿势是**结构性收益优先**（换依赖 / 换后端，如 native-tls 一刀 −12%），
**代码层挤压最后做**（先跑 llvm-lines 用数据确认有靶子）。当前两者都已到头：
6.61 MB 无水分，**没有新硬需求（如分发渠道体积限制）就不要重启这条线**。
