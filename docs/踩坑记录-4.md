## 十六、录制内核（单文件方案）的失败根因链与修复（2026-10-06）

**路线决策**：录屏内核 = 旧版**单文件直写**方案（无分段、无拼接、无接缝）；分段拼接
方案整体弃用（终态快照 `.bf/1006-1425 新版终态-彻底弃用/`，只取知识、不回搬代码，
本册 §十一–§十五的分段专属知识按历史参考读）。其余功能全量保持新版——两世界以
`src/platform/{recorder,audio,audio_capture}.rs` 三个文件为界。

### 失败根因链：卡死与产物损坏是同一条链

编码器忙时节流反压楔住录制线程，或空音频流让 `Finalize` 撞 ~10 秒内部等待
（只在"当时恰好没声音"时出现——"不确定性失败"的那个不确定就是它）→ 收尾在调用
线程无限 join → UI 冻结 → 用户强杀 → `moov` 没写 → 产物打不开。

### 三道修复（不改变产物特性）

1. sink 属性 `MF_SINK_WRITER_DISABLE_THROTTLING=1` + `MF_LOW_LATENCY=1`（与 §十三同源）；
2. 音频断流 > `SILENCE_FILL_MIN_HNS`(200ms) 才补静音，流永不为空；
3. 收尾限时：`finish()` 15 秒；`finish_detached(timeout, on_done)` 把收尾整个挪到
   后台线程，结论经 `runtime::record::REC_FINISH_NOTICES` 槽位回 UI——软件本体
   绝不被收尾拖死。看门狗数据源 = `RecProgress`（stage + 每帧心跳 stamp_ms），
   UI 按 `REC_STALL_GIVEUP_MS`(60s) 停摆主动结束并报"卡在「X」第 N 帧"。

### ★★★ 音频时间线必须内容驱动（"电流声"根因）

每批音频的 `SetSampleTime` 用**上一批的结尾**（`audio_ts_next += 批时长`），
**禁止**用视频帧 ts 打戳：批里内容是"自上次 drain 攒到的任意长度"，与帧长对不齐
⇒ 时间线频繁缺口/重叠 ⇒ MF 丢内容 ⇒ 碎片化声音。参考音标记法实测（`rec_tone` +
`audio_e2e` 探针，Goertzel 定位 1760Hz 标记）：错位打戳下 5.000s 标记间隔两次缩成
4.86s（140ms 内容被吞），机器后台声音被碎成 RMS 119 的残渣——碎片化就是用户听到
的"电流声"；内容驱动后 8/8 标记精确 5.000、纯音 RMS 与理论值精确一致。

连带：短缺口（<200ms）**不要**补静音——那等于把连续音频拦腰插 0，每个插点都是
一次波形跳变；真实样本下一帧自然续上，音轨整体滞后几毫秒听不出来。
音频时间线与视频时间轴的长期漂移（设备时钟 ppm 级）在小时级录制才可感，暂不处理。

### 判据

- `tests/record_smoke.rs`：正常录 8s 产物有 `moov`；`CURSEEN_REC_FAULT_AFTER` 注入
  中途错误后 `finish` 如实报错且产物仍被 `SinkFinisher` 收尾可播。两用例必须

- `tests/probes/rec_tone.rs`（录制）+ `tests/probes/audio_e2e.rs`(解码)：
  标记间隔全 5.000、非标记区无管线自造噪声。

## 十七、录制的结构性隔离：采集/编码解耦 + 出进程（2026-10-06/07）

§十六那三道修复解决的是"出错时能收尾"，但采集、转换、编码、收尾仍在**同一条线程**
⇒ MF/DXGI 卡住就是整条链一起停，而且卡住的那条线程还占着**桌面复制进程级单例**
（之后一次都录不了，只能重启软件）。两道结构改动把"卡死"从"会传播"变成"可隔离"。

### A. 采集 / 编码解耦（`run_mp4` 一分为二）

两条线程，中间只以**系统内存字节**过界：采集侧 `sync_channel(6)` 满即**丢帧**
（`dropped+1`，绝不阻塞采集节奏）；音频 drain 后同样过界，但**音频绝不丢**
（发不出去攒到下一批，时间线仍连续）。编码侧**自带 D3D11 设备与设备管理器**，
采集侧从此完全不碰 Media Foundation。

- ★★★ **XVP（VideoProcessorMFT）配了 D3D 设备后只吃 DXGI 样本**：喂系统内存样本恒报
  `Input Sample has no DXGI buffer (0x80004002)`。过界的字节必须在**编码侧重新长成
  纹理**再包样本，不能 `MFCreateMemoryBuffer` 直接喂。
- ★★★ **采集侧楔住 ⇒ 没人写 `moov` ⇒ 内容全丢**。编码线程不能阻塞等
  （`recv_timeout(500ms)`），停止位已置且 1.5s（`ENC_IDLE_GRACE`）无新帧就
  **自行 Finalize** —— 这才是楔住场景下"不丢内容"的真正保险（实测采集侧楔住时
  产物 100KB 有 `moov` 可播）。
- ★ 看门狗只看采集心跳会漏掉"编码器楔住"（解耦后采集照常出帧）：两条停摆放一起
  取**较大值**；阶段也拆成采集 / 编码两份，否则停摆提示指错地方。
- ★ 判据语义变了**：楔住冻结判据看 `written()`（写入帧数），**不是** `frames()`
  （采集帧数）—— `encode` 楔住时采集侧照常出帧，用 `frames()` 永远等不到冻结。

### E. 出进程隔离（`curseen-rec.exe`）【已废弃：2026-10-07 收回进程内】

> ★★ **2026-10-07 用户拍板：不再独立子进程，录制收回主进程线程**（`Backing::Child`
> / `rec_bridge.rs` / `rec_host.rs` / `rec_child_crash` 探针整体删除）。理由：子进程
> 1.79MB 只是"同样代码再链接一遍"的重复份，功能上不新增任何能力。**接受的代价**：
> 录制线程楔住后杀不掉，桌面复制单例被占 ⇒ 只能重启软件（`wedged` 如实上报，
> UI 提示"录制卡住，需重启软件才能继续录"）。`killed` / `crashed` 字段随之删除。
> 以下小节保留当时踩坑记录（命名共享内存 / 进程存活判据等知识可复用），涉及
> "双载体"的表述以本注为准 —— 现在只有进程内线程一条路。

`Recorder` 新增 `enum Backing { Thread{..}, Child{mirror, child} }`，**对外接口一行没变**
（runtime / UI 零改动）。过界只有两样：**一块共享内存**（`RecMirror`，`repr(C)` 全原子，
主建子开）+ 进程句柄；参数走 JSON 临时文件（命令行传不下 + 中文路径转义易错）。
命令只有 `stop` 一个原子位；子进程侧 20ms 同步线程兼三件事：转发 stop、刷进度、
检测主进程存活（防孤儿占住桌面复制单例）。

- ★★★ `OpenProcess` 必须带 **PROCESS_SYNCHRONIZE**（`PROCESS_QUERY_LIMITED_INFORMATION`
  不含它）；存活判据 = `WaitForSingleObject(h, 0) != WAIT_OBJECT_0`（进程活着 →
  `WAIT_TIMEOUT`）。别用 `GetExitCodeProcess == STILL_ACTIVE`（退出码恰好 259 的应用存在）。
  判据写反时**第一帧之前就把自己停了**，报 `MF_E_SINK_NO_SAMPLES (0xC00D4A44)`。
  另加防抖：连续 10 次（200ms）判不在才真停 —— 单次误判毁掉整段录制比孤儿更糟。
- ★ `MapViewOfFile` 在 windows 0.62 **不返 `Result`**（返 `MEMORY_MAPPED_VIEW_ADDRESS`，
  失败看 `.Value.is_null()`）；`OpenFileMappingW` 首参是 `u32`（要 `.0`）。
- ★★ **楔住后能不能再录，取决于载体**：`FinishOutcome` 新增 `killed` —— 子进程被强杀
  ⇒ 桌面复制单例随进程销毁 ⇒ **可以直接再录**（UI 说"已终止，可以重新录制"）；
  进程内线程楔住仍是死局（`wedged && !killed` ⇒ "需重启软件"）。这是出进程隔离
  相对"进程内降级"**唯一**的实质差别，必须由判据钉住。
- ★★★ **子进程"自己没了"必须判 `done` 位，不能只看"进程退出了"**：崩溃 / 访问违例 /
  被外部杀都**绕过** `host_main` 末尾的 `done.store(1)`，而主进程眼里是"按时退出 +
  镜像无 error"⇒ `is_clean()` 为真 ⇒ 界面把缺 `moov`、打不开的产物报成"录制完成"
  （2026-09-19 同款判断点换载体复活）。`FinishOutcome` 因此新增 `crashed`：
  `exited && done == 0` 即置位，合成"子进程异常退出（退出码 N）"，且**不算 `wedged`**
  （进程都没了 ⇒ 单例已释放 ⇒ 可以重录，别再提示重启软件）。
  判据 `tests/probes/rec_child_crash.rs`：先录一段正常的断言 `is_clean()`（正面），
  再用 `TerminateProcess` 杀掉子进程断言 `!is_clean() && crashed`（反面），最后验
  "崩溃后能立刻再录"。崩溃无法按需注入，只能杀 —— 杀就是最接近的复现。
- ★ 降级：子进程 exe 不在时 `spawn` 失败即回退进程内线程（功能不丢）。
  逃生口 `CURSEEN_REC_IN_PROCESS=1`；探针指路 `CURSEEN_REC_HOST_EXE=<路径>` ——
  **测试二进制在 `temp/target/release/deps/` 下，同目录永远没有那个 exe，不指路
  必然降级**，`build/probe.py` 已默认自动指路（`--in-process` 才走降级路径）。
- 部署必须搬**两个** exe：缺 `curseen-rec.exe` 时 `build/deploy.py` 在报告里写
  `REC_SRC_MISSING`（静默降级 = 少一层隔离，必须显眼）。

### 判据与实测

- `tests/probes/rec_wedge.rs`：`CURSEEN_REC_WEDGE_AT=acquire|encode|finalize` 在指定阶段
  **永久阻塞**。四条断言：收尾回调限时到达、期间 UI 心跳线程持续推进、结论
  `wedged=true` 且错误带阶段名、强杀后再录一段仍能出帧。
  实测（`encode` 注入，子进程路径）：采集 **59** 帧 / 写入 **10** / 丢弃 **42**，
  收尾 3.08s 返回、UI 心跳 263 次、产物 126KB、`killed` ⇒ 再录 61 帧干净收尾。
- ★ 注入点在第 11 帧（`maybe_wedge` 的 `tick >= 10`）：判据若只等"帧数够不够"会在
  注入生效**之前**请求停止，线程正常退出 ⇒ 判据变成"测了个寂寞"（第一次跑就是这样
  红的）。非 `finalize` 阶段要等**帧数冻住**（≥1.5s）才认定注入生效。
- ★ 错误文案判据认**语义**（"收尾超时" / "未退出"），不认具体措辞 —— 否则换一次实现
  就要改一次判据，而真正要保证的是"绝不当成完成上报"。
- `capture_smoke` 子进程路径 10/10；音频 48.21s 录制 → 音轨 47.723s（固定编码偏移，
  与 18s 版一致 ⇒ 不是丢尾部）。

### 三条分钟级短测（长测覆盖不到的分支，2026-10-07）

2 小时联动长测（216003 帧 / 30.0fps / 丢 4 帧）证明的是"**稳定工况**下不坏"。它
跑不出下面三类分支，而这几类恰恰是日常最容易撞的 —— 每条都是分钟级，可随时复跑：

- **`tests/probes/rec_env_shock.rs`（环境突变：改分辨率）**：录制中途
  `ChangeDisplaySettingsW` 切到 800×600 停 6 秒再切回，逼 `AcquireNextFrame` 返回
  `DXGI_ERROR_ACCESS_LOST` 走重建分支 —— 长测里这条分支**一次都没走到**。
  判据是"如实"而不是"必须救回来"：报完成就必须突变后**还在出帧**，没出帧就必须
  带 `error`；另外收尾 <30s（不许楔）、`crashed` 必须为假、突变前的帧不能在产物里
  消失、显示器必须复原（不留给环境副作用）。
  实测（1920×1080@60Hz → 800×600@60Hz）：帧数 **181 → 373 → 566**，收尾 0.12s、
  无错误、产物 9.98MB / 视频样本 565 ⇒ **重建成功、录制没断**。
  锁屏 / UAC 安全桌面不自动化（会留下等用户交互的安全桌面），留作人工试用项。
- **`tests/probes/rec_load60.rs`（高负载：60fps）**：楔死的历史诱因是**编码器反压**，
  而 30fps 长测里编码器全程游刃有余（丢 4 帧 ≈ 没压到）。帧率翻倍 = 编码吞吐翻倍，
  是最省事的反压来源。判据：收尾 <30s、实际 ≥54fps、丢帧率 ≤2%、产物有 `moov`。
  实测 300s：**18001 帧 / 稳定 60.0fps / 丢 10 帧（0.06%）/ 收尾 0.14s / 570MB**，
  逐段（每 30s）全是 60.0fps —— 没有周期性塌陷。
- **`tests/probes/rec_rapid_cycle.rs`（连录 + 跨类型切换）**：桌面复制是**进程级单例**，
  上一段没收完新一段就建不起来；历史上这里的表现不是报错，而是**界面一直挂着"在录"**。
  故钉的是"如实告知"：起不来必须 `Err`（带原因），起得来必须真有帧真有 `moov`，
  且单例最终要释放（歇 2 秒后再录必须成功 = 泄漏检测）。末尾再跑一轮
  MP4 → GIF → MP4 不等收尾的切换（快捷键连按的现场）。
  实测：8/8 段成功、被拒 0 次、每段收尾 ~0.1s；MP4/GIF/MP4 三切换全干净
  （GIF 45 帧、带 `GIF89a` 与 trailer）。

- ★★ **不在责任范围内的三类，明确不做**：断电、磁盘写满、系统级强杀进程组 ——
  这些是环境灾难，不是软件缺陷（`moov` 只在最后一次 `Finalize` 写，这三种情况下
  仍会丢）。（子进程强杀覆盖判据 `rec_child_crash` 已随出进程隔离废弃删除。）
- ★ 主进程侧 `Recorder::out_size()` 在**子进程路径下返回 0×0**（尺寸只有子进程知道，
  没回传镜像）——只影响诊断打印，不影响功能。

### §17.9 ACCESS_LOST 重建退避改三段带（2026-10-07）

- 原实现：`duplicate_with_retry` 固定 10 次 × 50ms（最坏 0.5s）——慢速模式过渡
  （改分辨率/驱动重置 1~2s）撑不过去就会"桌面复制失效且无法重建"体面收尾。
- 新实现：三段带 25ms×10 → 100ms×20 → 500ms×10，总窗口 **7250ms**（分级退避：
  带内计数、逐段放宽；总时长按我们
  "重建不了就收尾"的语义收紧）。映射在纯函数 `dup_retry_sleep(attempt)`，
  单测 `dup_retry_sleep_follows_three_bands` 钉死各段边界与总窗口 7250ms。
- 实测：`rec_env_shock` 绿（1080p→600p 切换，突变前 181 → 后 563 帧，
  收尾 0.10s、丢弃 2、错误 None、显示器复原）。
- 出处：同路线录屏项目通用的分级退避方案（2026-10-07 研读）。

### §17.11 出进程隔离切断了录制合成通道（2026-10-07，用户报告"录屏里没有放大画面"）

- **症状**：屏幕上放大正常，录出来的视频没有任何放大效果。0928 建的「录制合成」
  通道（`capture_share`：面板位图 → `Session::pump` 贴进采集纹理）本是好使的，
  1007 录制搬进 `curseen-rec.exe` 后静默失效——**发布端（`PipWindow::present`）在
  主进程、消费端（`snapshot`）在子进程，进程内静态槽跨不了进程**。老快照（0930）
  还是进程内载体 ⇒ 用户记忆"老版本支持"正确。
- **修法**：槽本体改**命名文件映射**（跨进程），API 换 `publish`/`clear`/`snapshot`；
  enabled 旗标也搬进共享控制页（两个进程谁 open/drop 都写同一页）。seqlock 同步
  （写两段递增 seq，读端前后一致才收；写端 30FPS、读端 30FPS，撕裂帧直接丢弃）。
  进程内线程载体走同一份映射，两种载体行为一致。
- ★★★ **映射名前缀后不允许再出现反斜杠**：`Local\CurSeenPipShare\sXXXX` 在
  `OpenFileMappingW` 直接 `ERROR_PATH_NOT_FOUND`（0x80070003），子进程永远读到空槽。
  平名无反斜杠（`curseen-pipshare-sXXXX`）即好——与 rec_bridge mirror 命名同款。
  靠"打开失败必留痕"的日志一次定位。
- ★★★ **判据必须解码视频像素且防桌面杂红污染**：第一版全帧 bbox 被浏览器图标 /
  任务栏的红点撑大（1062×1052 vs 面板 320×180）⇒ 误报"没有红块"（假红）。
  正解 = 期望矩形内红像素占比（≥90% 命中）+ 行序双假设自校验（top-down/bottom-up
  只有一个命中；MF 解 RGB32 的行序与 DEFAULT_STRIDE 属性都不可靠）。
- **MF 解码 RGB32 两个坑**：① 必须给 SourceReader 开
  `MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING`，否则 `SetCurrentMediaType`
  拒收 0xC00D36B4；② `ReadSample` 出参全 Option（windows 0.62）。
- 探针 `rec_pip_share`（双载体）：发布纯红测试帧 → 录 4s → 解码前 3 帧判面板区
  占比。顺带修 probe.py `--in-process` 被 REMAINDER 吞掉静默不生效的坑（与 `--secs`
  同款，前置摘除）。
- 主进程 `finish()` 的 Child 分支补 `set_enabled(false)`：子进程被杀/崩溃时没人执行
  Session::drop 的清理，别让发布通道悬挂在"开着"。

### §17.12 两路音频混音没按时间对齐 ⇒ 回音 + 音轨被拉长 1.59 倍（2026-10-09）

- **症状**：用户报告「录屏时系统声音有回音感」，判据是"点系统音量那声叮"。
  ★ 关键限定：**只在麦克风与系统声音同开时出现**——只开系统声音时全链路干净
  （脉冲间隔精确 1000ms），所以排查第一步必须先确认配置。
- **根因**：`AudioCapture::take_samples` 用 `max(mic.len(), spk.len())` 把两路按
  **buffer 内相对位置**逐样本相加。两路是两条独立线程、各自 100ms 缓冲、各自被
  WASAPI 事件唤醒，谁先到谁排在前面 ⇒ **第 i 个麦克风样本和第 i 个系统声音样本
  根本不是同一时刻的声音**。后果分两条：
  1. **音频被拉长**：两路交替到达时 `Σ max(micᵢ, spkᵢ)` 逼近两倍单路 —— 本该 1 秒
     的音频被写成近 2 秒。实测 3 秒真实时间：单路 **0.970 倍**、两路同开
     **1.593 倍**。写进 MP4 后音轨比视频长得多，音画不同步。
  2. **回音**：系统声音走 spk 直达，又被麦克风拾到走 mic 路，两路错开后相加。
     实测每个脉冲后面跟着一个 **+20~30ms** 的重复脉冲（幅度与主脉冲相当）。
- **修法**（`audio_capture.rs`）：① **起点只对齐一次** —— 首次两路都到齐时，
  两路 buffer 的长度差正是"启动时间差 × 采样率"，丢掉先启动那路多出的前置样本；
  ② **逐轮取 min** —— 只输出两路都到齐的部分，慢的那路余量留到下一轮（不丢）；
  ③ **另一路真停了**就退回单路语义（堆积超 `LANE_STOPPED_I16`＝0.5s 的量），
  否则快的那路会无限堆积。修复后实测：单路 0.973、**两路同开 0.980**，成对脉冲归零。
- ★ **回音不是声学现象，是软件 bug**：修完串音本身仍在（麦克风照样拾得到外放），
  但它与直达声**同时刻**相加，只是响一点，不再产生可分辨的重复。区分二者的
  唯一办法就是拿脉冲串量时间轴，不能凭"有麦克风就会串音"想当然。
- **判据**：探针 `tests/probes/audio_echo.rs`（fast 组）—— `rate_check` 量两路速率、
  `capture_echo` 量成对脉冲、`rec_echo` 走完整 MP4+AAC 后解码、`denoise_delay` 量
  降噪延迟；单元测试 `mix_*` 三条锁住新语义（取 min / 起点只对齐一次 / 另一路停了）。
  ★ 信号必须用**稀疏脉冲串**（每 1s 一个 40ms burst），连续正弦看不出重复。
- **两个附带实测**：
  - **loopback 在没有任何程序发声时一个包都不产**（"只开系统声音 + 静音"抓到
    **0 个样本**）。这既是 recorder 静音填充存在的前提，也是"等两路到齐"必须
    加兜底的原因——不对就没有第三条修法，会直接卡死。
  - **RNNoise 给麦克风信号加 5~10ms 延迟**（off=0 / weak=5 / medium·strong=10ms）
    且改变波形（weak 档整段 RMS 只剩 70%）。它**只作用于麦克风路**（`run_capture_loop`
    里只有 `is_mic` 才建 `MicProcessor`），不碰系统声音；但会**加大**两路错位，
    所以降噪档位确实是回音的加重因素，不是主因。

### §17.13 两路音频「声音比画面慢」：静默期双重计量 + 起点对齐过早（2026-10-09）

- **症状**：§17.12 修完回音后，用户紧接着报「没有回音了，但**声音明显比画面慢**，
  测了多次都如此」。判据仍是"点系统音量那声叮"。
- ★ **第一道坎：常规场景根本测不出来**。用 `av_sync`（连续 440Hz + 每 5s 标记）
  和稀疏脉冲（整段静音、每 5s 一标记）各测一次，偏移都是 **+33ms（声音略早）**、
  标记间隔精确 5.000s、斜率为噪声级 —— 全绿，与体感完全相反。
  原因：**这两种模式下播放会话一直存在，loopback 一直产包**，静默期的行为被掩盖。
- ★ **破局：复现"平时完全没播放会话、突然响一声"**。给 `build/av_marker_driver.py`
  加点击模式（`AV_CLICK=1`）：只在白闪那一瞬播一声 0.3s 短响，播完会话即结束。
  一跑就露馅 —— 偏移 **−513 / −416 / −316 / −216 / −86 ms**（负 = 声音晚），
  且**随录制时长累积**。单路（只开系统声音）同场景却是 ±70ms、中位数 +0.2ms
  ⇒ **问题只在两路交互**。
- **根因两条（都在 `AudioCapture::take_samples`）**：
  1. **静默期双重计量**（造成累积漂移）：旧实现判定"另一路真停了"用**堆积量**
     （0.5s 的样本数）。系统静默时 loopback 一个包都不产，`min = 0` ⇒ 麦克风路
     一路堆到 0.5s 才吐一次，而这期间 `take_samples` 一直返回空 ⇒ 录制层按视频
     时间线**补了静音**、时间线照常推进；等那 0.5s 积压吐出，时间线**又推进一次**。
     两边都推进 = 音轨被拉长 ⇒ 越录越慢。
  2. **起点对齐过早**（造成恒定 170ms）：`aligned` 在**首次 `take_samples`** 就用
     `swap(true)` 置上，而那时两路 buffer 往往**都还是空的**（长度差测成 0）。
     两路设备的初始化有先后（实测差 ~170ms），先启动那路于是**永久积压**，
     而取 min 永远消化不掉这个积压 ⇒ 那一路的声音永久滞后。且**追不回来**：
     落后量小于录制层补静音的 200ms 阈值，补齐永远不会触发。
- **修法**：
  1. 判定"另一路真的没声音"改用**等待时长**（`LANE_IDLE_WAIT = 60ms`）而不是堆积量。
     60ms ≈ 2 帧（30fps），远大于一个 WASAPI 包周期（10ms）不会误判抖动，
     又远小于补静音的 200ms 阈值，双重计量的窗口根本打不开。★ 且**持续静默期间
     每轮都直接输出**（不再"等一轮"），否则快的那路又会堆积。
  2. 起点对齐只在**两路都真的到齐**（都非空）时才做并置 `aligned`；还没到齐时
     **直接按有的那一路输出，绝不等待**。另一路起来/恢复时，它的第一个样本正好
     对应"那一刻"，而另一路的消费位置也走到那一刻（静默期间没消费过它），
     天然对齐，不会积压。
- **实测结果**：−513/−416/−316/−216/−86（累积漂移）→ 修完第 1 条 **−170ms 恒定**
  → 修完第 2 条 **+30 ~ +57ms**（与单路 ±70ms 同一水平），去斜率波动 **29.6ms**。
  回音判据未复发（8 个脉冲间隔精确 1000ms），两路速率 0.980 倍。
- **判据**：`tests/probes/av_sync.rs` 新增 `av_lag`（自录 20s + 白闪/标记同钟比对，
  `AV_LAG_CLICK=1` 开点击模式、`AV_LAG_MIC=1` 开麦克风）。分析主体抽成
  `analyze_av(inp, min_pairs)` 与长录共用。★ 判据要打印**逐对明细**，
  光看"固定偏移中位数"会把"恒定滞后"和"累积漂移"混为一谈。
- ★ **教训**：判据全绿而用户体感红时，**先怀疑场景没复现**，而不是先怀疑判据算错。
  信号设计必须匹配用户场景 —— "静默里的一声短瞬态"和"连续音"是两种完全不同的
  代码路径（一个有播放会话、一个没有）。

### §17.14 录屏「显示光标」产物里 I-beam 闪烁：GDI 直写桌面复制纹理（2026-10-09）

- **症状**：TIM 里输入数字，录出来的视频里 I-beam 光标一闪一闪；**实屏正常**
  （用户确认只有视频闪）——闪烁是录制管线自己引入的。
- **取证**（探针 `tests/probes/cursor_flicker.rs` 的 `cf_analyze`，帧差法逐帧解
  用户真产物 1920×1080/272 帧）：块 (800,704) 变化 **93/272 帧**，逐帧暗像素
  `10↔0` 交替——约 1/3 的帧光标**凭空消失**（该帧均值=纯背景）。间隔 3~8 帧
  不均匀，与桌面更新节奏相关。
- **根因**：`draw_cursor` 用 GDI（GetDC + DrawIconEx）**直接写在 `acq`**——
  那是桌面复制的活跃纹理。桌面持续更新（TIM 有动画/重绘）时，GDI 写入与
  该纹理的 GPU 生命周期竞争，部分帧的写入被下一帧覆盖/丢弃 ⇒ 光标间歇缺失。
  静屏场景（几乎全超时帧）竞争窗口打不开 ⇒ 合成复现测不出来，只有真实
  持续更新的桌面才露馅。
- **修法**（`recorder.rs`）：加 **clean / work 双纹理**。fresh 帧时
  `CopyResource(clean, acq)`（干净底图）；面板合成画在 clean 上（同为 GDI
  通道，同样必须离开 acq）；每帧 `CopyResource(work, clean)` 后 GDI 画光标到
  work；回读读 `read_tex()` = 显示光标 ? work : clean。GDI 从此只碰自己的
  纹理，与桌面复制彻底解耦。附带把 `ci.flags != CURSOR_SHOWING` 改成按位测
  （CURSOR_SUPPRESSDISPLAYCAPTURE 可与 SHOWING 同置，等值比较会整帧跳过光标）。
- **复现/判据**（`cursor_flicker` 测试 + `build/cursor_blink_driver.py`）：
  驱动窗 = 类光标 IDC_IBEAM + 鼠标停正中 + 插入符 2Hz + **ANIM_MS=33 动画色块**
  （制造持续 fresh 帧，这是复现的关键条件）。判据 = **稳定性**：光标框暗像素
  均值 >0 且帧间跳变率 ≤5%。改前（动画场景）均值 2.2 / std 3.0 / 0↔15 振荡；
  改后恒 4 / std 0 / 跳变 0，判据绿。
- ★ **三个判据坑（全踩了一遍）**：
  1. 静屏 + 超时帧重复画的假设是**错的**（I-beam 纯黑单色，重复画幂等，
     实测逐帧恒定不闪）——判据全绿而用户体感红，先怀疑场景没复现。
  2. "可见帧"阈值（暗像素≥10）在缩放 0.667 + 4:2:0 下失当（黑柱只剩 ~4 个
     暗像素）——闪烁的本质是**帧间振荡**，判据要测稳定性不是绝对可见数。
  3. 驱动窗的三个坑：没置顶被别的窗盖住（判据假绿）；`SetCursorPos` 不产生
     WM_MOUSEMOVE、类光标不生效；`LoadCursorW` 第二参是 **MAKEINTRESOURCE
     整数**（32513），传字符串 "IBeam" 得 NULL、`SetCursor(NULL)` 直接把
     光标藏了（flags 全 0）。探针必须校验 hCursor 句柄 + 框内背景亮度。


## 十八、剪贴板面板粘贴在 QQ/TIM 落空（2026-10-07）

### 症状与日志取证

面板行点击粘贴在 QQ/TIM 输入框落空 + 目标播放错误音，notepad 一直好使。
日志（build/log）证据：每次都是"前台切换 ok=true + saved_ok=true 两条相差 1ms"，
随后 SendInput 无效——**API 全部返回成功 ≠ 内容到货**，日志判据到此为止。

### 四层根因（逐层剥开，都在 `clipboard_history.rs`）

1. **粘贴目标冻结**：`last_foreground` 只在 show_panel 记一次。置顶面板下
   "点目标应用→点面板行"，粘到的还是开面板时的旧窗口。修 = `WM_ACTIVATE`
   WA_INACTIVE 时刷新 + `TARGET_POLL_TIMER` 500ms 轮询兜底（textus
   remember_foreground_target 同款）。
2. **面板必须正常激活（2026-10-07 晚定案，推翻当日早间的 MA_NOACTIVATE 方案）**：
   驱动实验对照（`temp/panel_drive` + 取证日志）钉死：面板被点击激活（TIM 走完
   失活→再激活周期）⇒ 粘贴到货；`WM_MOUSEACTIVATE` 返回 `MA_NOACTIVATE` 让 TIM
   保持前台 ⇒ MISS。机制：不激活时写回剪贴板触发 TIM 自己的剪贴板助手气泡弹出
   又消，前台被打成 **0x0 悬空**、TIM 内部焦点丢在已销毁的气泡上，Ctrl+V 落空
   报错误音；完整激活周期才能让 DirectUI 把焦点恢复到输入框。textus（TIM 下
   粘贴可靠）正是故意让窗口激活（其 main.rs 注释：不设 WS_EX_NOACTIVATE）。
   现行 = 不拦截 WM_MOUSEACTIVATE，切前台回目标交给 do_paste 既有流程。
3. **批量化注入不认**：一次 `SendInput` 打包 4 事件 + 右 Ctrl，QQ/TIM 不认
   （落空+错误音），notepad 认——这就是"notepad 好使 QQ 不行"的来源。
   修 = `send_paste_keys_textus`：逐个单事件 SendInput、每键 10ms sleep、
   左 Ctrl(0x11)+EXTENDEDKEY、失败保证 Ctrl 抬起；发键走独立线程不占消息泵。
4. **焦点手术无效**：切前台后立刻 AttachThreadInput+SetFocus，QQ NT（CEF/Qt 系）
   内部焦点没挂回输入框，注入键落在过渡态；60ms 后 `focus_inside` 依然 false
   （DirectUI 的焦点模型 Win32 看不懂）。修 = 整条删除（AttachThreadInput/
   SetFocus/WM_PASTE 直发全删），只留"切前台 → 等前台稳定 → 发键"。

- **修复** = 用户建议的"模拟点击标题栏"：`clear_appstart_latch()`，首开
  show_panel 时把光标移到顶栏计数区中心（`count_rect()`，拖动区里离搜索框/
  按钮/页签最远），**SendInput 注入真实左键单击**（进系统输入队列；PostMessage
  不算输入、无效），30ms 后还原光标；每进程一次（static AtomicBool）。
- 判据纪律：用户手点有效 ⇒ 修法必须注入"同类事件"（真实输入），而不是"看似
  等效的 API 调用"；修三次不中时回头查"测量环境与用户环境的差异清单"。

## 十九、`ureq` 换 `native-tls` 省 1.1MB：看着赚了，实测会让一半 HTTPS 站点连不上（2026-10-08）

背景：本仓「小而美」，一直在找体积优化。依赖源显示 `ureq` 拖进了 `rustls` +
`ring`（密码学实现），而 Windows 自带 **Schannel**——直觉上换成 `native-tls`
就能整机摘掉它们。**实测体积收益确实最大**：exe 7.51 MB → **6.44 MB（−1105 KB，
−14.4%）**，是当时能想到的单项最大收益。但这条改动**最终整条撤回**，过程与
抵掉它的两个缺陷都值得留下：

### 缺陷一：`native-tls-no-default` 变体在本版本里根本不可用

- 症状：编得过、跑起来 HTTPS 请求立刻 panic ——
  `uri scheme is https, provider is NativeTls but feature is not enabled: native-tls`。
- 根因：`ureq` 用 `cfg!(feature = "native-tls")` 判定 provider 是否可用
  （`src/tls/mod.rs` 的 `is_feature_enabled`），而 `-no-default` 变体在
  `Cargo.toml` 里写的是 `dep:native-tls`——按 Cargo 规则，`dep:` 语法**不会**
  生成同名 cfg feature。于是「依赖装了、feature 没开」这种半成品状态成立。
- ★ 更阴的地方：它的默认 provider 是 `Rustls`（`#[default]`），所以只改 feature
  不改构造处，**连 panic 信息都会指向另一个 provider**，容易误判成 feature 冲突。

### 缺陷二：换成带根证书的 `native-tls` ⇒ 部分站点握手失败（决定性的）

该变体强制拖 `native-tls-webpki-roots`，把这批根证书塞给 Schannel 当自定义
roots。同一台机器、同一时刻、同一批 URL 的对照实测：

| 站点 | `rustls`/ring | `native-tls`/Schannel |
|---|---|---|
| `gitee.com/api/v5/...`（更新检查） | ✅ 200 | ✅ 200 |
| `example.com` | ✅ 200 | ❌ `unable to find any user-specified roots in the final cert chain` |
| `www.baidu.com` | ✅ 200 | ❌ 同上 |
| `api.openai.com` | ⏱ 超时（本机网络） | ⏱ 超时（同） |

三个可达站点里挂两个。AI 对话窗与 `ext:http` 的 URL 是用户自己填的**任意**
HTTPS 地址，这个失效率不可接受 ⇒ **整条撤回**，`Cargo.toml` 里留了警示注释。

### 反转：真正可行的写法是「native-tls + `RootCerts::PlatformVerifier`」（已落地）

上面的对照做完后回头翻 ureq 源码，发现失败并不是「native-tls 不行」，而是
**没让它用系统根**。ureq 的 `tls/native_tls.rs` 按 `tls_config.root_certs` 分支：

```rust
RootCerts::Specific(certs) => { disable_built_in_roots(true); add_valid_der(..) }
RootCerts::PlatformVerifier => { disable_built_in_roots(false); }   // ← 真正的系统根
#[cfg(feature = "native-tls-webpki-roots")] _ => { disable_built_in_roots(true); webpki 根 }
#[cfg(not(feature = "native-tls-webpki-roots"))] => panic!("需显式配 root_certs")
```

默认是 `RootCerts::WebPki`，于是命中最下面那条打包根分支——**这才是崩的主因**。
显式指定 `PlatformVerifier` 后 `disable_built_in_roots(false)`，native-tls 就不会装那段
双重校验回调（`imp/schannel.rs`），改由 Windows 系统根完成验证：

- **收益仍在**：exe 7.51 MB → **6.61 MB（−921.5 KB，−12.0%）**（比内置根版少省 183 KB，
  是 `tempfile` / `vcpkg` 等**非 Windows 目标**依赖的残留，不进本产物）。
- **连通性 6/6 全 200**：gitee / example.com / 百度 / api.github.com / microsoft / bing，
  含原先失败的两个。
- **顺带变好**：信任链交给系统 ⇒ 自动跟随 Windows 更新，也天然兼容企业代理 /
  私有根这类「只在系统库里配过证书」的环境。README 要求 Windows 10/11，
  Schannel 的 TLS 支持没有缺口。

> 由此也解释了为什么 `-no-default` 那条路一定会炸：它把 `cfg(feature="native-tls")`
> 排除掉之后，既不满足 provider 自检，又必然落到最后的 panic 分支。

★ 两个条件必须同时满足：`features = ["native-tls", ...]`（**不能**是 `-no-default`）
+ `root_certs(RootCerts::PlatformVerifier)`。都已写进 `platform::http::agent` 与
`Cargo.toml` 注释，改前先看那两处。

### 判据纪律（本案最大的教训）

1. **编译通过 ≠ 功能可用**：缺陷一是运行期 panic，编译期和生产 advisory 都看不出来。
2. **一个站点 200 ≠ 链路没坏**：只拿更新检查（gitee）验证会得出「改造成功」的
   结论——但它恰好是唯一正常的那个。**多站点、同条件、同时刻的对照**才是判据。
3. **别照依赖树估体积**：同一轮里另一个假设（`env_logger` 拖 `regex` 白占体积）
   实测节省 **0 KB**——因为 `src/` 零使用，链接器 `/OPT:REF` 早就把它剪掉了。
   依赖树看着吓人，实际一个字节都没进 exe。**要么测 exe 字节数，要么别下结论。**

### 顺带收下的东西（零体积代价，已保留）

- 三条链路原本各建各的 `ureq::Agent`（超时口径 60s / `TIMEOUT_SECS` 各写一遍），
  收敛成 `platform::http::agent(timeout)` 一个构造点，provider 显式写出。
  实测最终体积与改造前**逐字节相同（7879680 B）**，行为等价；好处是再动 TLS
  feature 时只需改一处，不会重演本案的 panic。
