# CurSeen 踩坑记录（三）

> 续 `docs/踩坑记录.md`（§一–§五）与 `docs/踩坑记录-2.md`（§六–§十）。本册自 §十一 起。

## 十一、录屏（MF / DXGI）

### 11.1 `timeout=0` 不等于"立即返回"（★★★）（2026-10-05）

现象：录制长跑后线程**永久**停在「抓帧 `AcquireNextFrame`」，心跳停摆几百秒不恢复。

上一轮的结论是「已把 `AcquireNextFrame` 改成 `timeout=0`，线程**不可能**楔在采集步」。
**这个结论是错的。** `timeout=0` 的语义是"**最多**等这么久"，不是"一定立刻返回"；驱动/DWM
进入某种状态时，调用内部可以持有同步点不释放 —— 实测停在它上面 441 秒。

**铁律**：不要把"某个 API 有超时参数"当成"它一定会按超时返回"。要证明它可靠，得**逐次量
它自己的墙钟耗时**并设阈值判据，而不是靠"没报错就没事"推断。

### 11.2 楔死的真因：采集设备被交给 MF 造成互锁（★★★）（2026-10-05）

上面那条现象的**真因**不是 DXGI 不可靠，而是一处**我们自己**的互操作禁忌。

同机A/B 浸泡实验（各跑一次，条件对齐：同屏、同样有画面变化）：

| 臂 | 时长 | 调用/帧数 | 结果 |
|---|---|---|---|
| 纯采集（DXGI + GDI，**完全不碰 MF**） | 7200s | 436368 次调用 | 零楔死，单次最长 43.8ms |
| 生产链路（+ MF硬编） | 1259s | 35987 帧 | **楔死**在「抓帧」，停摆 60s 不恢复 |

⇒ 43 万次调用零楔死，**否掉"驱动层不可靠"**；唯一变量是 MF 有没有参与。

机制：`Session::open` 用 `IMFDXGIDeviceManager::ResetDevice` 把**采集那台** `ID3D11Device`
交给了 MF，于是硬件 H264 编码器与 VideoProcessorMFT 经 `MF_SINK_WRITER_D3D_MANAGER`
在 **MF 自己的工作队列线程上异步**读它。而 `ID3D11DeviceContext` 是**单线程语义**对象：
采集线程在 `AcquireNextFrame` 内部等驱动同步点的同时，MF 线程在等同一台设备的空闲 ⇒ 互等成死锁。
特征恰好"概率性、长时才复现、然后永不返回"。

**修法**：MF 改用**独立**的 D3D 设备（`enc_device`/`enc_context`），采集设备只服务 DXGI + GDI。
跨设备不能直接 `CopyResource`（D3D11 禁止），链路改为
`acq → gpu_mid →(staging)→ Map读 → UpdateSubresource → enc`。
验证：同一条命令 1800s 段从"第 1259s 楔死"变成"跑完 1800.4s 零楔死、54013 帧 30fps 恒定"。

**铁律**：把 COM/D3D/MF 这类**能跨线程共享的资源**交给别人之前，先问"它的线程模型是单线程
语义吗"。单线程语义的对象被两个线程各自异步使用时，死锁不是"可能"，是迟早。

### 11.3 楔死时"抢救收尾"救不回来（2026-10-05）

`finish_detached` 的抢救逻辑（`stage∈{Startup,AcqFrame,CopyFrame,Overlay}` ⇒ 接管 `Finalize`）
**判据是对的**，实测也确实走了它 —— 但产物仍然没有 `moov`（1.18GB 只有 `ftyp`/`uuid`/`mdat`
且 `mdat` size=0）。

原因：`Finalize()` 自己也要等编码器与设备队列排空，**而那台设备正被卡死的线程握着** ⇒
`Finalize` 自己也挂住了。凡"靠另一个线程收尾"的设计，都要问一句"**那个线程楔住时谁来收**"。

**推论**：11.2 修好之后这条救不再被触发，但它不会自己消失 —— 换采集 API / 换编码器
之后仍可能撞上别的楔点。判据与超时必须留着。

### 11.4 跨设备搬像素的三个 D3D11 坑（2026-10-05）

修 11.2 时连踩三个，**编译期全无感，只在真跑时暴露**：

1. `create_texture` 的第 6 参是 `MiscFlags` 而**不是** `Usage` —— 传 `D3D11_USAGE_STAGING`
   给它等于什么都没做（`Usage`/`CPUAccessFlags` 硬编码在函数里）。
2. **staging 纹理 GPU 写不进去**（`BindFlags` 恒为 0），`CopyResource` 拿它当目标报
   `0x80070057`。必须经一张普通纹理（`gpu_mid`）过渡。
3. `CPU_ACCESS_WRITE` + `Map(D3D11_MAP_READ)` 是**自相矛盾**（要 `MAP_READ` 就得
   `CPU_ACCESS_READ`）⇒ 同样 `0x80070057`。**GPU 能否写 staging 与 `CPUAccessFlags` 无关。**
4. `windows` 0.62 已无 `MapSubresource`/`UnmapSubresource`，只有 `Map`/`Unmap`，
   out 参数是 `Option<*mut D3D11_MAPPED_SUBRESOURCE>`。

**铁律**：D3D11 的资源创建参数是**一对**（`Usage`/`BindFlags`/`CPUAccessFlags`），
**单看一个合法不构成"配对了"**。改完必须真跑一次，只看编译过是不够的。

### 11.5 检查 MP4 时要处理 64 位盒长（2026-10-05）

自查产物时扫顶层盒，**超过 4GB 的 `mdat` 用 `size==1` + 8 字节扩展长度**。只判
`size==0`/普通 32 位的那版脚本会漏扫后面的 `moov`，误报"产物缺 moov"—— 假红。
（判据比被测物更严/更笨都会假红，与 `render_probe` 那次同源。）

**铁律**：写任何"扫文件结构得出结论"的脚本，先拿一个**已知正确的样本**验它自己。

### 11.6 音频流 0 样本 ⇒ `Finalize` 挂在 ~10 秒级等待上（★★★）（2026-10-06）

现象：180 分钟压测 57 次段切换**全部** 9.9~10.5 秒（历史有声音流动时只要 119~260ms），
56 次共吃掉 9.3 分钟真实画面，摊薄后"实测帧率 28.4fps"。

定位：对账日志显示**第 1 段的音频 take 就是 0**（此前"从第 2 段起挂"是对账日志在
`seg_index += 1` 之后打印、把上一段的账记到新段头上的**标号错位**）。全程 0 条 ERROR
—— 采集线程没死：探针只开扬声器 loopback，系统没放声音时 loopback **一个包都不产**，
take=0 是"正常的静音"。真正的 bug 是：**音频流整段 0 样本时，MF 的 MP4 sink
`Finalize` 会等一个随段长增长的内部等待**（10s 段实测 ~0.9s、180s 段实测 ~10s，
收尾占切换耗时 90%+）。

修复（`recorder.rs`）：take 为空时按**视频时间轴**把缺量补成静音 0 样本
（48kHz×2ch ⇒ 96000 样本/秒，单次封顶 1 秒），音频流永不为空。
A/B 实测（`CURSEEN_REC_AUDIO_STALL=1` 模拟采集零产出）：收尾 800~980ms → **9~14ms**，
整次切换 ~1050ms → **120~156ms**，产物恢复音轨。静音本来就该是 0，语义无损；
"真实采集/静音填充"在音频对账里**分开计数**，填充不得污染对账口径。

**铁律**：① 带音频的 MP4 段，音频流**一个样本都不能少写**——静音也要写；
② 对账日志的标号/口径错位会把排查引向完全错误的方向（这次把"全程零音频"误读成
"第 2 段起线程挂死"），对账打印必须在被计量的对象归位**之前**取号；
③ 环境变量开关（`CURSEEN_REC_AUDIO_STALL` / `CURSEEN_REC_NO_SILENCE`）让"采集
零产出"在任何机器上可确定性复现——判据要能自己红一次。

## 十二、编译成本与测试分层

### 12.1 全 `#[ignore]` 的探针不该登记成 `[[test]]`（2026-10-05）

现象：改一行代码后 `cargo test --release` 要 **1 分 55 秒**，而只编门禁本体要 1 分 29 秒。

根因：`tests/probes/` 下十一条探针（需真实声卡 / DXGI 采集 / 真实窗口）用 `[[test]]`
显式登记，于是 cargo 每次都把它们**编成独立测试二进制**（本机 11 个，每个 7~9MB）——
而它们**全部是 `#[ignore]`**，跑起来 0.00 秒。即"编一大圈、什么都不跑"。

cargo 只自动发现 `tests/*.rs`（**不递归子目录**），所以**不登记就不参与编译**。

| 配置 | 二进制数 | 耗时 |
|---|---|---|
| 登记探针 | 16 | 1 分 55 秒 |
| 不登记（现状） | 5 | 1 分 29 秒 |

**铁律**：判"要不要进默认编译"看的是**它跑不跑**，不是它有没有价值。全部 `#[ignore]`
的目标应移出默认编译路径，按需登记（`build/probe.py`）。

### 12.2 `[[example]]` + `required-features` 对探针行不通（2026-10-05）

本仓已有该先例（`gen_icon` 靠它避开 optional `resvg`），于是第一反应是照抄。
**但探针是 `#[test]]` 集合，没有 `fn main`**，改完 `cargo test --test capture_smoke`
**直接不存在了** —— 拿"跑不了"换"省编译时间"，不划算。
且 `required-features` 对 `[[test]]` **无效**（只有 `[[bin]]`/`[[example]]` 支持）。

**铁律**：换机制前先问"旧命令还能用吗"。省下 26 秒却让探针不可执行，是亏的。

### 12.3 临时改配置类脚本必须"无论如何都还原"（2026-10-05）

`build/probe.py` 要临时往 `Cargo.toml` 写 `[[test]]` 登记。`try/finally` 是底线：
**编译失败、Ctrl-C、探针 panic 三种情况都要还原**。
已用"注入语法错误→ 跑→ 验md5 与跑前逐字节一致"反向验证过。

★ 自查时踩的一个小坑：判断"是否已有登记"最初写成 `"[[test]]" in orig`，
而这个字符串**在注释块里出现过** ⇒ 每次都误报"已有登记"。
按行首整行匹配（`re.search(r"^\[\[test\]\]$", orig, re.M)`）才对。
**又是判据比被测物松的那一类**（同§11.5）。

### 12.4 "综合联动"必须真驱动，不能拿 sleep 占位（2026-10-05）

死锁（§11.2）是在**纯录制**下复现的，但真实使用时录屏从来不是单独跑的：拖尾、悬浮标、
点击波纹各有自己的 `FxCore`（Lua 引擎 + 每帧 `advance` + `render`），
**多条GPU 管线并发**才是死锁最容易暴露的场合 —— 而这些组合此前一条都没测过。

新增 `tests/probes/soak_link.rs`：固定时长内**真**起 `Recorder` + **真**加载三个
`FxCore`（`glow` / `solid` / `disc`），每帧 `move_to`/`press` + `advance` + `render`
写进真 `DrawList`。60秒实测：录制 1802 帧（**30.0fps 恒定**）、拖尾与悬浮标各1800
活动帧、点击波纹 435 帧、停摆 1–2ms、容器时长差 0.11%。

★ **判据要能自己红一次**：把判据②门槛抬到天上后确实报红并指出是哪条管线，
  恢复后复跑绿。这条纪律对"新写的测试"同样适用，不只对既有判据。

### 12.5 驱动真实 exe 的路子在本机走不通（2026-10-05，已放弃）

先试过"起真的 `curseen.exe` + 合成按键触发录制"，两处都撞墙：

1. **exe 自我提权重启**（`main.rs`：非管理员 → `ShellExecuteW(runas)` → 本进程退出）。
   ⇒ `Popen` 拿到的进程**1 秒内自己退出**（码 0），真身是提权副本，`proc.poll()`
   永远看不到它。日志原文：「提权副本已发起，本进程退出」。
2. **提权进程普通权限杀不掉**（`taskkill` 拒绝访问）⇒ 无法"先清场再测"；
   而残留实例的钩子已失效，实测合成 `F9` 日志**完全无记录**、录制没起来。

⇒ 结论：**联动测试不要走进程外按键**，改为在进程内直接驱动各模块
（`FxCore` 是 `pub` 的，`DrawList::new()` 也是 `pub`，headless 完全够用）。
已把那个 `build/soak_link.py` 删掉—— 留着一个跑不通的脚本比没有更糟。

### 12.6 开音频录制必崩：0xC00D4A3E（2026-10-05，全面联动抓出）

现象：录制开着系统声音，约 **100 帧后**报
`ProcessOutput 失败: 示例分配器当前为空，因为有未决请求。(0xC00D4A3E)`，整段作废。
关掉音频则一切正常（30fps 恒定）。

根因：`0xC00D4A3E` = **`MF_E_SAMPLEALLOCATOR_EMPTY`**。音频轨的
`sink.WriteSample(1, ..)` 让 SinkWriter 异步处理，多出来的音频轨会让**视频转换器**
这边留一个尚未取走的结果；此时再 `ProcessOutput` 就被拒。
它和 `MF_E_TRANSFORM_NEED_MORE_INPUT` 一样**不是错，只是"这一帧没有"**，跳过即可。

修法：与另两个码一起收进 `mft_busy()` 单一判据（见 §12.9）。

★★★ **这条 bug 为什么此前没人发现**：门禁里所有录制测试**都不开音频**；
`capture_smoke` 也不开（音频另用 `audio_probe` 验，那是**解码端**不是录制端）。
⇒ **"开音频录制"这条路径此前零覆盖**，只有"多模块同跑"的联动测试才碰到它。

### 12.7 凭错误码**名字**猜 = 白改一次（2026-10-05）

第一次修时把 `0xC00D4A3E` 认成了 `MF_E_INVALIDREQUEST`，改完"没生效"。
实际查windows 0.62 源码：

| 常量 | 值 |
|---|---|
| `MF_E_INVALIDREQUEST` | `0xC00D36B2` |
| `MF_E_SAMPLEALLOCATOR_EMPTY` | **`0xC00D4A3E`** |

**铁律**：处理一个陌生错误码，先在 windows crate 里 `grep` 它的**十六进制值**，
确认名字与值对应；名字相近的两个码值可能差很远。凭字面猜 = 改了个不相干的分支，
还会因为"看起来修了"而放过。

### 12.8 判据要能区分"死锁"与"提前退出"（2026-10-05）

15 分钟那跑在 92 秒时报「① 录制线程死锁」，但阶段是**「已结束」**、帧数停在 100——
录制**自己退出了**（因12.6 那个错），心跳停摆只是**后果**。
两者混为一谈会把排查指向完全不同的方向（"为什么驱动卡住" vs "为什么代码报错退出"）。

**铁律**：判"卡死"要同时看**阶段**与**帧数是否还在推进**；
`stage == Done` 时停摆是必然结果，不能当死锁证据。

### 12.9 MFT 有队列：四个"暂时不接"的HRESULT 都不是错（2026-10-05）

15 分钟联动实跑在**第 220 秒**抓到第二个码：
`ProcessInput 失败: 被调用方当前没有接受进一步的输入 (0xC00D36B5)`。
而§12.6 那个码在**第 100 帧**就出。两次都让整段录制作废。

⇒ VideoProcessorMFT 是**有队列的流水线**，队列满 / 输出未取走时它会拒收新样本，
**语义是"稍后再试"而不是"出错"**。四个码：

| HRESULT | 常量 | 含义 |
|---|---|---|
| `0xC00D36B5` | `MF_E_NOTACCEPTING` | 没有接受进一步的输入 |
| `0xC00D4A3E` | `MF_E_SAMPLEALLOCATOR_EMPTY` | 分配器为空（有未决请求）|
| `0xC00D6D52` | `MF_E_TRANSFORM_NEED_MORE_INPUT` | 需要更多输入 |
| `0xC00D36B2` | `MF_E_INVALIDREQUEST` | 无效请求 |

修法：收成单一判据 `mft_busy()`（`recorder.rs`），`ProcessInput`/`ProcessOutput`
共用；命中就当"这帧没进去"，照常走本轮余下步骤（写音频、心跳、节拍），**不 return**。
另加一条：`ProcessInput` 没成功时**不去取输出**（输入都没进去，此时 `ProcessOutput`
报的只会是连锁错误）。

**为什么这类 bug 此前零发现**：门禁里所有录制测试都不开音频；
短烟测（12~60 秒）也跨不过 220 秒这个点。**只有"固定时长 + 多模块同跑"才照得出来。**

## 十三、帧率归因与 SinkWriter 节流

### 13.1 帧率腰斩的真因：SinkWriter 默认节流（★★★）（2026-10-05）

现象：真实配置（**开系统声音 + 6 条特效管线同跑**）下，30fps 设定只跑 **15.8fps**，
产物本身完好（`moov` 齐全、双轨都在、时长差 0.20%）—— **不是产物坏，是帧率不对**。

上一轮的分段计时把每帧归到 4.24ms，而 15.8fps 的周期是 63.3ms ⇒ **约 59ms 无归属**。
定位它的关键不在代码，在**没被打印的量**：`AcqCost` 里的 `loop_us`（主循环整体墙钟）、
`sleep_us`、`pip_us` 三个字段**采集了却全仓无任何读取点**，`rec trace` 只打 6 段
⇒ **定位缺口所需的量恰好就是没打印的那几个**。

补上打印后，缺口落到 `IMFSinkWriter` 的**默认节流**上：它按实时速率节流（为"边录边播"设计），
本项目主循环**自己定速**（`frame_deadline` 按绝对时刻对齐），多出来的那层节拍在
**开音频**时额外阻塞——音频轨让 SinkWriter 内部要交错两轨，AAC 编码器与视频 MFT 争抢
同一个工作队列，背压直接落回主循环的 `WriteSample`。

修法（`recorder.rs` `create_sink_writer_inner`）：设
`MF_SINK_WRITER_DISABLE_THROTTLING=1` + `MF_LOW_LATENCY=1`。

验证（同一条命令、真实配置）：

| | 修复前（900s） | 修复后（600s） |
|---|---|---|
| 实际帧率 | **15.8 fps** | **30.0 fps** |
| 逐段曲线 | 710s 后塌到 ~1fps，靠追帧补回 | **每 10s 严格 +300 帧，全程零抖动** |
| 各段合计 / 周期 | 4.24ms / 63.3ms | 33.18ms / 33.33ms |
| **未归账** | **~59ms** | **0.15ms** |
| 容器时长差 | 0.20% | 0.04% |

★ 判据纪律：第一次只跑 90s 就看到 30fps，**但那不算数**——上一轮的退化在 220s 才触发，
90s 根本没跨过拐点（正是 §12.9 那条"短烟测跨不过 220 秒"）。**必须跑到 600s 逐段看曲线**，
才敢说"拐点被消除"而不是"平均数被掩盖"。

**铁律**：
1. **`IMFSinkWriter` 默认按实时速率节流**。自己定速的实时录制**必须**给
   `MF_SINK_WRITER_DISABLE_THROTTLING=1`；离线重写也要给（§7.1 已记）——**同一条铁律的两处应用**。
2. **"没报错"不等于"没开销"，"没打印的量"更不等于"不存在"**。定位性能缺口前，
   先确认**所有分段都被打印**；本例缺口正好落在没打印的字段上。
3. 计时口径两条陷阱：① `acc_conv`（"转换"）**已包含** `copy_to_encode`，父子不可相加；
   ② `sleep_us` **在掉帧时天然为 0**（`frame_deadline` 是绝对时刻，落后越多越不会进 sleep），
   但**帧率正常时它就是主动睡眠**——本例修好后它占 28.50ms，两种情形都要会读。

### 13.2 桌面复制失效：从"一次失败即结束"改为带退避的持续重试（★★★）（2026-10-05）

问题：`ACCESS_LOST` 的语义是"**等系统过渡完再来**"，但原实现重建一次不成
就 `return Err` ⇒ **用户切一次全屏游戏 / 拖一下显示器 / 驱动更新，就废掉整段录像**。
这正是"录一两个小时"最不能接受的失败方式。

修法：重建循环 `DUP_RETRY_MAX=40` 次，退避 `250ms → ×2 → 上限 2s`（覆盖约 1 分钟窗口），
仍不成才体面收尾（`Finalize` 补 `moov`，已录那段仍可播）。
参考：同类桌面复制采集实现对 `ACCESS_LOST` 按无限重试处理；微软官方样例给三档退避 `{250ms×20 → 2000ms×60 → 5000ms}`。

### 13.3 一个**方向相反**的错误码错值（★★★）（2026-10-05）

修13.2 时顺带发现：`duplicate_with_retry` 的 `FATAL` 集合里写着
`0x887A0007` 并注释成 `NOT_CURRENTLY_AVAILABLE`。查微软官方错误码表：

| 常量 | 官方值 | 语义 |
|---|---|---|
| `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE` | **0x887A0022** | "稍后再来" |
| `DXGI_ERROR_DEVICE_RESET` | **0x887A0007** | GPU 已被重置，"**重新创建设备并继续**" |

⇒ 两个**语义完全相反**的码被混为一谈。后果很严重：把 `DEVICE_RESET` 当
"同一时刻只容一份桌面复制"而立刻放弃，等于**驱动每次重置都直接废掉整段录像**。

修法：① `FATAL` 改用真值 `0x887A0022`；② `DEVICE_RESET` / `DEVICE_REMOVED` /
`DRIVER_INTERNAL_ERROR` 归入新的 `is_duplication_lost()`，走 13.2 的重建退避。
③ 门禁 `device_loss_codes_are_recognised_by_their_official_values` **按官方值逐个钉死**
（已反向验红：漏掉 `DEVICE_RESET` 确实报红并点名）。

**铁律**：这是 §12.7「别凭错误码名字猜值」的**第二次**同型翻车，而且这次是
**方向相反**（把"可恢复"当成"不可恢复"）。写判据时**先查官方表**，代码里**用常量名**
而不是手写魔数，让"名字↔值"由`windows` crate 保证对应关系。

### 13.4 跨设备搬像素的"共享纹理"路线**走不通**（★★★）（2026-10-05，重要否定结论）

§7.1 那条"独立编码设备 + staging 中转"每帧要付 4.00ms（1080p 8MB 往返）。
按 §7.5 的方向试了**共享纹理句柄**（`gpu_mid` 建时带 `MISC_SHARED`，编码侧
`OpenSharedResource` 拿同一份显存，再在 `enc_context` 上 `CopyResource`）——
**编译全绿，真跑全废**：

- 探针判据④报红：容器时长 38.33s / 墙钟 90s（**差 57%**），`moov` 齐全但**视频轨只 1150 个样本**（应 2700）。
- 取证（临时在 `mft_busy` 两处写文件计数，45 秒共 1350 帧）：
  `ProcessInput` 被拒 **1250 次** `0xC00D36B5MF_E_NOTACCEPTING`，`ProcessOutput` 仅 1 次。

根因：`sample_from_texture` 用 `MFCreateDXGISurfaceBuffer(..., fCompatible=false)`
把纹理交给 MF，它要求纹理**对 MF 可读**。跨设备共享显存满足"能拷"，但**不满足
"MF 能读"** ⇒ 转换器逐帧拒收。**共享句柄解决的是"跨设备拷贝"，不是"给 MF 读"。**

⇒ **已回滚**到 staging 中转（重新验证：30.0fps / 时长差 0.20% / 未归账 0.15ms）。
**双缓冲（两张 bridge 交替）也没做**：它要引入一帧（33ms）延迟，而 30fps 下已有
27ms 余量——**拿音画失步的风险换 3ms 不划算**（用户口径：稳定性优先）。

**铁律**：D3D11/MF 这类改动**编译通过什么都不能证明**（本项目已连踩多次：
`CPU_ACCESS_WRITE`+`MAP_READ`、`staging` 的 `BindFlags`、本条的共享纹理）。
**判据只能是"真跑一次 + 查产物结构"**，而且**要查样本数**——
"帧数对、时长对"仍可能藏着"样本少一半"（时间戳按墙钟算，样本少了时长就短）。

### 13.5 ★★★ WGC 换路：两个"只能实测发现"的坑（2026-10-05）

WGC（`Windows.Graphics.Capture`）替掉 DXGI 桌面复制，动机是结构性的：
`AcquireNextFrame` 实测**永久卡死 441 秒**，而 WGC 是 DWM 推帧、代码里不存在
"等新帧"的阻塞点；且 WGC **没有"全进程只容一份"的进程级单例** ⇒ GIF 与视频可同时录。
2026-10-05 原型 + 生产模块 + 接入全部完成，真机探针 5/5 全绿。

#### 坑一：★ 请求 BGRA，回来的是 **RGBA**
向帧池**请求** `B8G8R8A8UIntNormalized`，实测回来的字节序**是 RGBA**
（标记 RGB(224,160,16) 读成 (16,160,224)，**绿通道精确对上、红蓝互换**）。
照 BGRA 解释 ⇒ **所有颜色红蓝反，且不报错**。
**唯一发现它的办法是拿一个"已知颜色的标记"去对** —— 读文档、读代码都发现不了。
判色一律走"红蓝可互换 + 绿通道精确"。

#### 坑二：★★ 判据 `mvhd` 会被**音频轨掩盖**，造成假绿
现象：WGC 录 600s，`容器时长: 600.18s（差 0.02%）✅ 全绿`，而实际产物是
**视频轨 10461 样本 / 348.70s**、音频轨 600.18s、文件 350MB（应有 610MB）。

根因：`mvhd` 是 **Movie Header**，时长取所有轨的**最大值**。音频轨正常时会
**把视频轨的截断完全盖住**。而 `soak_link` 判据④只看 `mvhd` ⇒ **判据比被测物松 ⇒ 漏报**。

⇒ 已加 `mp4_video_sample_count()`（在视频轨的 `stbl` 里找 `stsz`），
判据④ 现在**先判视频轨样本数**再判总时长。改完当场抓到上面那个坏产物。

**铁律**：查录屏产物**必须看 `stsz` 样本数**，不能只看墙钟/帧率/总时长 ——
"帧数对、时长对"仍可能藏着"视频轨只剩三分之一"。

#### 坑三：★ 忙拒收计数当时压根没被记
`mft_busy` 命中时只置了局部 `frame_converted = false` 就扔了，**全仓无任何计数**。
只能靠"样本数差 × 帧长"反推。已加 `AcqCost::convert_busy` / `output_busy`。
★ 另：**诊断打印必须印在所有断言之前** —— ④号断言 panic 会把后面的成本/忙拒收/
后端打印全跳过，判红时恰恰拿不到最需要的数据（为此白跑一次 10 分钟）。

**实测对应关系（这次终于对上了）**：忙拒收 7540 次 vs 缺样本 7539 个 ⇒
**每一帧被 MFT 拒收 = 容器里少一个样本**。

## 十四、被否定的方案：样本槽位池（2026-10-05，已删除）

忙拒收时期设计过"8 槽位池"（`platform/sample_pool.rs`，对齐 wcap 的
`ENCODER_VIDEO_BUFFER_COUNT 8`）：预建 8 个 `IMFSample`，槽位耗尽时**不丢帧**，
而是 `IMFSinkWriter::SendStreamTick` 送一个时间刻度进容器，让"这 33ms 没有画面"
这件事在时轴上自洽。

**结论：A′ 换成同步 compute shader 之后它不需要了**——槽位池治的是"**异步**转换器拒收"，
同步 dispatch 结构上不存在拒收，槽位永远不会耗尽（wcap 的 8 个槽位其实从未被填满，
同一个道理）。已于 2026-10-05 删除该模块（判据：全仓 `grep` 只剩 `mod.rs` 里一行
`pub mod`，零调用者、零测试）。

★ 留下来的知识：**槽位归还必须走 `IMFTrackedSample`**。`ProcessInput` 返回后 MFT
**仍持有**该样本，我们不知道它何时读完；自行判断"写完 SinkWriter 就还槽位"，会在 MFT
还在读的时候**覆写同一份显存** ⇒ 画面撕裂 / 花屏，且不报错。只能让 MFT 用完时通过
`IMFAsyncCallback::Invoke` 回调归还。这条对任何"复用显存喂编码器"的设计都成立。

**铁律**：否定一个方案时要**连带删掉它的代码**，只留结论——留着 251 行零调用者的实现，
模块头还写着"定位到的硬伤根因"，下一个人会以为它还在工作。

## 十五、★★★ `moov` 单点：为什么"录几小时失败就全没"（2026-10-05）

### 现象

长录制在**看不出规律**的时刻失败，产物几百 MB 却打不开，录了多久全白费。
5 分钟、30 分钟、2 小时、10 小时都出现过。

### 根因：**失败概率与录制时长基本无关**

MP4 的索引 `moov` **只在最后一次 `Finalize` 时才写**。录制全程，磁盘上的东西是
`ftyp + mdat` —— 一堆**没有目录的原始数据**。于是：

> 任何一次没走到 `Finalize`，录 90 秒和录 10 小时的结果**完全一样：全丢**。

时长只改变"暴露在这个窗口里多久"，不改变"失败即全丢"。**这正是"看不出规律"的原因**——
找时间规律找错了方向，要找的是"哪些路径走不到 Finalize"。

### 铁证（`tests/probes/crash_loss.rs`）

录 90 秒后 `TerminateProcess` 硬杀子进程（等价于任务管理器结束 / 系统更新强制重启 /
驱动 TDR 带走进程）：

```text
产物：90178099 字节（86.0 MB）  含 mdat：true   含 moov：false  ⇒ 完全打不开
```

### 现有两道保险的覆盖边界（必须记住）

| 保险 | 前提 | 覆盖不了 |
|---|---|---|
| `SinkFinisher` 栈守卫 | **栈能展开**（panic / `?` 返回） | 线程卡死（栈不展开）、进程被杀 |
| `SinkSlot` 跨线程接管 | 卡在**采集侧** | 卡在编码/音频/收尾（并发 `Finalize` 未定义，**明确不能接管**） |

⇒ 十种失效里只有四种能保住数据。全丢的六种：进程被杀 / 断电蓝屏 / 卡在
`WriteSample`·`Finalize` / `Finalize` 自身失败 / 采集中断超 1 分钟 / 4GB 边界。

### 对策：把"最后一次写索引"改成"每过一段就写一次索引"

分段落盘（方案 C）：每 3 分钟或 1 GiB（先到先触发）就 `Finalize` 当前段并开下一段，
**每段自带 `moov`、独立可播**。最坏只丢最后一段。

★ 关键认知：**"绝对不出错"做不到**（进程被杀 / 断电 / TDR 都不在我们控制之内），
但**"出错也不丢"可以做到 100%** —— 只要任何时刻崩溃时，已录内容都已是成品。
用户要的底线是后者，不是前者。

### 实现四坑

1. **时间戳必须改段内基准**。新 sink 的第一帧若沿用全局时钟，段开头会凭空多出
   "上一段那么长"的空白（播放器先黑屏三分钟才出画面）。
2. **新段必须重新登记进 `SinkSlot`**：卡死抢救收的是**当前这段**，不是最老那段。
3. **`Finalize` 收完即清空槽位** ⇒ `SinkFinisher` 不会重复收同一段（两者共用同一 `Option`）。
4. **"有没有产物"不能再只看最终路径**：多段时那个 `.mp4` 根本不存在，内容全在
   `.parts/` 目录里。漏掉这步，界面会报"录制失败"而事实是录得好好的
   （用 `product_bytes` / `product_path` 统一取）。

### 副作用（白捡的）

- **4GB 边界自动规避**：每段封顶 1 GiB，全仓从未验证过 `IMFSinkWriter` 越过 4GB 的行为，
  现在变成"永远碰不到"。
- **锁屏 / 休眠可保段后续录**：分段天然支持"暂停-恢复"。
- **磁盘写满时已有段落全保住**。

### 判据

`python build/probe.py run crash_loss`（`CRASH_SEG_SECS` 调段长）。三条判据：
① 录出 > 1 MB；② 可播段数 ≥ 预期；③ **除正在写的最后一段外，每段都必须自带索引**。
（判据③防的是"段落盘了却是半成品"这种假绿。）

### 11.7 颜色修正三段史：自洽 ≠ 播放器认（★★★）（2026-10-06）

"颜色不对"修了三轮，每一轮的教训都不同：

1. **BT.601 limited + 不声明** ⇒ 播放器按 full 解：黑 6% 灰、白 92% 灰（"蒙版"）。
   教训：数据与声明必须自洽（`apply_color_attributes` 四属性 + colr 盒）。
2. **BT.709 full + 全链路声明** ⇒ 端到端探针绿，用户实测**整体偏蓝**。
   教训：**判据自洽 ≠ 播放器认**。探针用 MF SourceReader 解码，它按声明解；
   大量播放器对 H.264 一律按「709 limited」默认解释、根本不读 colr/VUI ⇒
   full 数据被误解成对比度拉伸 + 饱和度 ×1.14，冷色调桌面读作"偏蓝"。
   **输出格式要选"所有播放器的公共默认"，声明只是锦上添花** —— HD H.264 的
   公共默认就是 709 limited（主流录屏软件同款）。
3. **BT.709 limited（现状）**：`color_e2e` 端到端误差 ≤1/255，真机 colr=1/1/1/full_range=0。

连带两小坑：
- limited UV 变换常数初版把"中性色度仍是 128（0.5）"算成了 0.060784，
  **yuv_probe 当场判红** —— 判据要能自己红一次，这次真的抓住了。
- `MF_MT_FRAME_SIZE`（UINT64）打包口径：**高 32 位 = 宽、低 32 位 = 高**。
  写反后视频处理器按 360×640 出图再信箱缩放，画面只剩中间一条色带，不报错。
