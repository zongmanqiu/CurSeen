## 六、帧驱动与常驻模块

### 6.1 共享时钟不能放在早退点之后（★★★）（2026-09-26）

拖尾永不消失。根因：`elapsed`（共享时钟）的更新在早退分支**之后**，而特效 `eff.step` 只听
`trail_enabled`、在循环体内门控 ⇒ "关着 A 还能跑 B"时，B 的时间戳**冻死**在最后一次 A 走到的位置。

**铁律**：带早退分支的 tick 里，**共享时钟绝不能放在早退点之后**。

### 6.2 新增常驻功能必过三道帧门（2026-09-26）

复合脚本"勾了没反应"。两个门的第一条件都是「该模块是否活跃」，一处修两处通。
**这是 park 态坑的第三次变体**（放大镜、拖尾、复合脚本）。

**三查**：`input_needs_frame` / `mouse_input_needed` / `frame_demand`，并进
`trail_module_active()` 两门同通——**缺一就是"勾了没反应"**。空闲 park 后不出帧。

### 6.3 编辑态**不**加"每帧续帧"（2026-09-22）

第一版把 `frame_up`（GIF 选框 **或** 编辑态）也接到 `request_repaint_in`，**是错的**：GIF 那条
是历史包袱（"边框要从蓝变红，这是唯一的状态信号"）；编辑态的屏面（冻结帧 + 压暗 + 工具栏）
**静止时一个像素都不变**，唯一的动态元素是光标放大镜，而它随鼠标移动走 ⇒ **自带一次重绘**。
再无脑续帧就退化成"整屏 CPU 软渲染以刷新率空转"。

**判据**：进入编辑态后**不动鼠标**，CPU 应回落到 ~0%。三处 `frame_up` 的用途要分清：
`partial` 判据与 `invalidate_spotlight` 用宽的（GIF 或编辑态），**续帧**用窄的（只 GIF）。

### 6.4 小键盘 Enter 与主区同 VK（★★★）（2026-09-26）

Windows 上小键盘 Enter 与主区 Enter 是**同一个 VK `0x0D`**，只能靠 `LLKHF_EXTENDED` 区分；
键码映射漏分支时，小键盘 Enter 会被认成主区 Enter。修好后热键串里 `ENTER` 与 `NUMENTER`
从此是两个键 —— **有意为之的副作用**。

同类：NumLock 关闭时，Windows 把小键盘 4 直接翻译为 `VK_LEFT (0x25)`（LL 钩子收到的就是
`0x25`），回显按功能语义显示 "←" 是**正确行为** —— 别急着当 bug 修。

### 6.5 脚本不改图（2026-09-27）

用户口径："源图背景全是黑色，产物里背景却变透明了——私自乱改图片。" 那套 `black_to_alpha`
（按亮度把黑底换算成 alpha）**整条删除**。脚本回到"**像素是什么颜色、图标就是什么颜色，
唯一处理是缩放**"。要透明底，请在**源图里**就把 alpha 画好（带 alpha 的 PNG 会被原样保留）。
护栏 `logo_is_not_blank` 钉死"0 个非不透明像素 + 黑底 >0"。

### 6.6 工具条与"拖选区"重叠时，工具条优先（2026-09-22）

选区几乎铺满屏幕时工具条会走兜底分支退回屏幕底边，而选区的**下边框带**很可能正好压在那里
⇒ 用户点按钮被当成"拖动选区"吃掉，表现为"按钮画着却点不动"，完全看不出原因。`toolbar_hit`
与 `begin_stroke` 必须用**同一个** `toolbar::hit` 与同一个锚点。

### 6.7 笔输入的「两条路」：直通与翻译层只能喂一条（2026-09-28）

数位板起笔约 0.5 秒的痕迹延迟，三轮才定位到**结构性错位**。笔的真实输入有两条路：
① 窗口的 `WM_POINTER` —— 笔尖一触系统即刻送达；② 系统「指针→传统鼠标消息」翻译层
补发的 `WM_MOUSE*` —— 前面挂着 Windows Ink 的手势消歧，起笔段被缓冲（**已知行为**，
应用侧没有任何掩码能压到零；`WM_TABLET_QUERYSYSTEMGESTURESTATUS` 只关手势、不关这条
缓冲）。本项目绘制由 `WH_MOUSE_LL` 钩子驱动，吃的只有 ② ⇒ 直通（windui 补丁 093）
接好了也白接；而要吃 ① 就必须让「只对笔」的事件进绘制，否则两路同喂 = 一笔画两遍、
还倒着画。

**铁律**：同一设备的多条输入路径，必须**选一条**喂给消费方 —— 用设备类型显式分路
（`windui::pointer_is_pen`）+ 钩子侧丢弃迟到副本 + **新鲜度兜底**（Up 万一丢失，1.5 s
自动恢复放行，绝不让全局输入被永久吞掉）。

同类坑：**「底图」必须和它的覆盖范围成对传**。马赛克取样连错三轮，根因是把「落码矩形」
统一当底图原点 —— 冻结帧覆盖**整张虚拟桌面**，于是永远取到屏幕左上角那块，用户看到的
就是「马赛克没有任何效果」。凡「位图 + 坐标」成对出现的接口，两个值必须同源产出。

### 6.8 事件回调里不能再借 `Runtime`；"起笔"的门不能用"正在书写"（2026-09-29）

一次笔点按把进程打挂，日志两行：`panic: RefCell already mutably borrowed` +
SEH 通道的 `0xC0000005`（两条通道各记一半，见 `platform::crash` 的模块文档）。

**根因一：在事件回调里借 `Runtime`。** windui 的 `on_event` 是在 `Runtime` **已被借用
期间**被同步回调的，里面再 `borrow_mut().feed(..)` 就是 `RefCell` 重入；而
`panic = "abort"` 下它不给你第二次机会，进程直接消失——用户看到的正是"一按就没了"。
**铁律：事件回调 = 只入队，不借款。** 要喂输入就走与鼠标钩子**同一个** mpsc
（`platform::input::hook::HOOK_TX`），由帧循环那侧统一 drain。

**根因二：门用错了量。** 笔直通的门写成了 `drawing.controller().is_drawing()`，
而它在**笔尖刚接触**时必然是 false（笔画还没开始）——于是"笔永远起不了笔"，只能干等
系统"指针→鼠标"翻译层迟到 ~0.5s 的那份 `MouseDown` 把笔画开起来，之后笔的 Move 才被
接管。**这就是用户三报"起笔延迟 0.5 秒"的真根因**，跟手势/压感/抓屏全都无关。
**铁律：判断"要不要接管这类输入"必须用状态（功能开没开，如 `DrawMode != Off`），
不能用结果（动作有没有发生）。** 拿结果当门 = 先有鸡还是先有蛋，功能静默降级成"只做
一半"，而且看起来特别像性能问题。

### 6.9 起笔延迟的真根因：标注态 NCHITTEST 恒回 HTTRANSPARENT，笔根本到不了本窗（★★★）（2026-09-29）

四报"起笔 0.5s 延迟"的终局定位；前三轮全在给一个**收不到消息的窗口**打补丁。

**链路**：标注态覆盖层已清 `WS_EX_TRANSPARENT`（`MouseMode::Interactive`），但命中测试最终听
`WM_NCHITTEST` 的**逐点回答**——`on_nchit` 只对截图编辑态、GIF 选区带、文字悬停带回 `Client`，
**漏了屏幕标注**，于是标注态对所有点回 `HTTRANSPARENT`，命中把笔送进桌面：`WM_POINTER` 一条
不来（093 直通死代码）、手势查询没人问（092 死代码），笔只能等系统翻译层因 press-and-hold 消歧
而**迟到 ~0.5s** 的鼠标副本。鼠标从没暴露这个洞：`WH_MOUSE_LL` 是全局钩子，不走命中测试。

| 轮次 | 改了什么 | 为什么没用 |
| --- | --- | --- |
| 一 | 关系统手势（windui 补丁 092：`WM_TABLET_QUERYSYSTEMGESTURESTATUS`） | 关的是 press-and-hold / flick，**不是**"指针→鼠标"翻译层自带的消歧缓冲 |
| 二 | 直吃 `WM_POINTER`（补丁 093） | 代码对着，但**一条都没送到**——日志里 `笔直通` 零命中（★ 判据：接线成功 ≠ 事件到达） |
| 三 | 把门从 `is_drawing()` 换成 `DrawMode != Off` | 门对了，可上游根本没有事件流过来 |

**RTS（换输入源）实测败退，已整模块删除**（`platform/input/stylus.rs`、`windows-core` 依赖、
`Win32_UI_TabletPC` feature、许可登记全部回退）：对照做法——用 RealTimeStylus 从
驱动直接取包（同类数位板直通实现的通行路线），本仓照此新增 —— 真机**挂载成功但 `StylusDown` 零事件**；且 RTS 挂上后**从不卸载**
（`mem::forget` 了 COM 对象），真机**书写十分卡顿、退出标注后整系统鼠标依然卡顿**：一条没用的
通道把输入管线挂住。沉淀两条：**换输入源成功与否要看事件计数**；占用系统级输入管线的对象
（钩子 / RTS / 捕获）**必须有对称的卸载路径**。

**顺带记下的 windows crate 细节**（下次直接抄）：`#[implement(IStylusSyncPlugin)]` 展开的代码用
**未限定**的 `windows_core::` 路径 ⇒ `windows-core` 必须是**直接依赖**（版本与 `windows` 锁定
一致）；`#[implement]` 生成的是 `<名字>_Impl`，接口方法要实现在 `Foo_Impl` 上；crate 没导出
`CLSID_RealTimeStylus`（在 SDK 的 `um/RTSCom_i.c`），须写死
`{E26B366D-F998-43CE-836F-CB6D904432B0}` —— **常量一律从本机 SDK 头取，不要凭印象写。**

**"分层窗吞 `WM_POINTER`"是误判**：对照 elite-pen 读它的**完整初始化**（窗样式 + 命中 + 消息处理
三件套），其书写窗就是 `WS_EX_LAYERED` + `LWA_ALPHA`，分层窗收指针消息毫无问题——只对照消息
处理分支就会得出"它行我们不行 = 底层差异"的假结论。真正该对齐的是它的输入拓扑：**它的窗口
永远是笔的命中目标**。

**修法**：`Runtime::drawing_owns_pointer()`（`DrawMode != Off`）并入覆盖层 `on_nchit`——标注一开
整屏回 `Client`，`WM_POINTER` 当帧落窗，093 直通整条链点亮；退出标注自动交还穿透。
回归锁 `drawing_owns_pointer_follows_draw_mode`。

**教训（方法论级）**：
- **"窗口收不到消息"先查命中测试，别先怀疑窗口样式**。逐层顺序 = 窗口存在 → 可见 →
  `WS_EX_TRANSPARENT` → **`WM_NCHITTEST` 逐点回答** → 消息处理分支。前两层都过了，第四层
  藏了四报 bug。
- **全局钩子会掩盖命中测试的洞**：鼠标走钩子一直正常，恰恰让"窗口其实收不到任何命中"藏了四轮；
  输入通道越兜底，越要主动验证主通道是否活着（打点计数）。


### 6.10 透明幕布：标注不冻结屏幕（2026-09-29 用户拍板）

用户口径：*"只要屏幕可以不冻结，依然可以看到下面的画面，应该就很不错了"*，且冻结帧
+ 每帧铺满整屏的光栅正是"标注时飙到 50 MB、书写卡顿"的大头。

- `start(Screen)` 不再抓屏：`Backdrop::None`，叠层自身透明，底下桌面照常活着
  （能看着任务管理器实时占用）。白板**不变**，仍冻结帧 + 白幕。
- 产物背景改为**保存那一刻**现抓桌面：`screenshot::grab_hiding(OVERLAY_TITLE, ..)`
  —— 先把覆盖层藏掉再抓，否则工具栏会被拍进产物（这正是旧"抓屏派"被否的原因）。
  抓不到就只出墨迹（透明底），绝不贴黑块。
- 马赛克在 `None` 下本来就只抓落码那一小块，无额外开销。
- 回归锁：`screen_annotation_is_a_transparent_curtain_not_a_frozen_frame`
  （Screen 必须 None、白板必须白幕）。

### 6.11 渲染图片缓存把"死位图"扣成每轮 16 MB 的泄漏（2026-09-29）

用户报"开关三次标注 20→70MB"。给留档链路埋 `PagefileUsage` 采样后逐步锁定：

- 合成一段 +24.3 MB（现抓底图 Rc 8.1 + 位图副本 8.1 + 合成缓冲 8.1）；
- 产物 drop 只回落 8.1；`stop()` 置 `backdrop=None` 后**纹丝不动**；
- `Rc::strong_count` 在 stop 时 = **2** —— 缓存外早没人了，第二份在
  `runtime/render.rs` 的 **`IMG_CACHE`**：条目 = `(键, (Rc<RgbaBitmap>, WImage))`，
  会话中每帧铺底图都命中它，退出后却没人清 —— 一条 = 8.1(Rc) + 8.1(WImage)
  = **每轮 16 MB**，和"三次开关 +48MB"严丝合缝。

**修法（两层）**：① `cached_image` 进入时 `retain(strong_count > 1)` —— 缓存外
没人持有的位图**永远不可能再被画**（画它必须持有 Rc），死条目立即清除；
② 标注退出路径显式 `clear_image_cache()`。

**教训**：
- **"用地址当键"的缓存必须持有 Rc**（防地址复用误命中），这同时也意味着**缓存本身
  是一份引用**——评估内存时不能只看业务对象的生存期，还要看"谁顺手攥了一份"。
- 泄漏定位别靠猜：`GetProcessMemoryInfo(PagefileUsage)` 埋在链路各步 +
  `Rc::strong_count` 两个埋点，一轮就把"哪一步、哪两块"钉死了（诊断探针
  `examples/mem_probe.rs` 可复用；外部采样提权进程不可靠，要用应用自报）。
## 七、验收方法论（判据本身的坑）

### 7.1 真机自动化必须**独占机器**（2026-09-22）

验收脚本报"墨迹与拖拽起点不符"，看起来像坐标系偏移 bug。**不是** —— 日志里有**不属于脚本**
的点击（托盘图标、菜单项……）：**跑自动化的时候人正在用同一只鼠标**。脚本两次注入被真人
鼠标覆盖，于是"点直线"实际落在"序号贴纸"cell 上。

**规矩**：真机验收必须独占机器（开跑前确认没人在动键鼠）；报告里留存
「**脚本注入值 vs 应用日志值 vs 像素实测值**」**三方对照**，只有三方一致时才允许把差异归因
给产品代码。

**配套**：验收脚本四条铁律 —— ① 必须**在一个提权子进程里跑完全部步骤**（执行环境按 Job
Object 回收派生的子进程，父进程一 `return` 整棵树被杀）；② 父进程要等 `=== DONE ===`，
不是"报告文件存在"（报告是分步追加的）；③ 点击前确认目标窗在前台
（`GetForegroundWindow() == h`），否则**不注入**（实测点进了 Chrome，还可能误操作用户的播放器），
结束用 `HWND_NOTOPMOST` 还原；④ 报告每条带**墙钟时间戳**，否则"按钮没变"到底是"真没变"还是
"截图拍早了"永远说不清。

### 7.2 判据不能建在被判对象上（2026-09-20）

写"透明 GIF 裁剪"的判据时**特意不复用 `FrameReader`** —— 判据不能建在被判对象上，
否则两边一起错就会一起绿。同理：比色表要比 `table_bytes()[..len*3]`，**不是**整段
`table_bytes()`（后者含补到 `2^bits` 的填充字节，拿它当判据是错的）。

### 7.3 只测"拨动"、只测默认值 —— 都是假绿（2026-09-21）

- **只测默认值固定点**抓不到量纲错：默认值换算后仍是默认值，**看起来自洽**。
  要逐字段取一个**非默认**的真实值走 `from_config → apply_to → 回原值`。
- **只测"拨动"也是假绿**：`set()` 会覆盖掉错误的初值，写端对了就绿，**读端的错被漏掉**
  （回退修复时这条确实仍然通过，才补上读端断言：初值必须落在默认倍率对应的刻度上）。
- 判据要有**增量**：新门禁先跑一遍**对旧代码真红**，否则不知道它防住了什么。

### 7.4 判据必须有**分辨力**，且必带**对照组**（2026-09-20~27）

- **分辨力先立住**：`INSET(GetWindowRect − EXT) = L7 T0 R7 B7` —— **非零才有分辨力**；
  若为 0，"贴边"就是假绿（两条路都能过）。
- **必带对照组**：否定型断言要同时断言"该被捕获的确实被捕获了"。反例：
  `!over_our_window(150,150)`（PID 比对）是**太弱**的判据，附近恰好有别的窗盖住该点就红；
  改成"取回来的**句柄**是不是替身窗"+对照组（不穿透的替身窗**必须**能被取到）。
- 少了对照就是"边框本来就没混色"的假绿、"按键链路死了"的假绿、"窗压根没盖住那个点"的假绿。

### 7.5 判据之间不许耦合（2026-09-23）

`if pan:` 把 ②③④ 全包在一个前提里 ⇒ 前提一倒，其余**静默跳过**，报告照样出、结论却是空的。
**判据独立化**。同类："正则字段必须与代码里的格式串**逐字对齐**"，否则整段断言被静默跳过，
而需求的核心判据正好在那一段里。

### 7.6 两条"读错工具"的坑（现象与"产品没生效"一模一样）（2026-09-23）

判据读错工具，现象与"产品没生效"长得一模一样，认不出：① **空串 = 热键停用**（守卫是
`!配置串.is_empty()`，注多少次都没反应，验收脚本必须**显式把热键摆上**）；② **日志按字节切、
按字符读**：`os.path.getsize()` 是字节、`f.read()` 是字符，中文一字 3 字节 ⇒ 增量窗口整体前移、
刚写的行被切掉，于是报"热键没生效"，其实是"没读到"（**一律按字节读写**）。
### 7.7 凡"差恰好 1"，先怀疑自己的含/不含约定（2026-09-23）

验收脚本 v1 的对比结果是 `(0, 0, −1, −1)`，结论行写着"扫描失败"。查下去是**判据自己的
off-by-one**：`out_left` / `out_up` 返回"最外侧窗口像素的坐标（含）"，而 `out_right` /
`out_down` 返回"**第一个背景像素**的坐标"（开区间端点）——两者**都已经等于矩形端点值**，
但 v1 给右/下又 `+1`。**同类（这条最贵）**：把"某个目录 / 文件已不存在"写成带日期的
**审计式说明**、还抄进 8 份文档共 30 余处，彼此矛盾 —— 现场结论**不要**写成日期戳式的审计叙述。
### 7.8 喂给反解的样本必须**物理自洽**（2026-09-23）

测试夹具第一版把"半透明边框压背景"的期望值随手写成 `(47,200,47)`，反解出来是
`(103,255,73)` —— **用例自己都不知道自己在断言什么**。改成物理自洽的
`obs = 0.6*bg + 0.4*118`。

**终局（2026-09-28）**：夹具再自洽也救不了反解本身——`bg` 是"边框后面被盖住的颜色"，
**物理上不可见**，怎么取都是猜（外侧 1px 常是 DWM 阴影/相邻窗）。反解整体删除，
边框像素原样保留（成熟截图工具的通行做法）。教训升级：**当"样本永远拿不到真值"时，
任何夹具精度都是在给一个无解模型抛光**——该删的是模型。

**推广**：「数某种字符的奇偶」这类判据，先拿一个**已知正确**的输入验一遍再写进断言
（曾经把"文件对话框过滤器必须成对"判成"NUL 个数是偶数"，而那恒为奇数 ⇒ 每一份正确的
过滤器都被判红；正确判据是**分段**：按 NUL 切开后段数为 `2n+2`、末尾恰两个空段）。

### 7.9 幂等判断必须按**实际字节形态**做（2026-09-27）

文件是 CRLF，按原始字节校验会报"0 份"的**假失败**，差点误判修复没生效。

### 7.10 点击类验收先证「注入能到达目标窗」，再判「按钮灵不灵」（2026-09-27）

- **现象**：非提权探针用 `SendInput` 点面板上的「打开文件夹」，`on_click` **一次都没触发**，
  可 LL 键鼠钩子的日志里**看得见**那次 `MouseDown`（"注入了、也收着了，就是没生效"）。
- **三组实验**（这是定性的关键，单看第一组只会得出"按钮坏了"）：① 点按钮 → 无反应；
  ② 改点一张卡的**标题**（已知能改 UI 状态：点一下该展开）→ **卡片也没展开**，落点处别的窗口
  被带到前台 ⇒ 连"注入能操作这个面板"都不成立；③ 探针**自己提权重跑**
  （`ShellExecuteW(None, "runas", py.exe, ...)`）→ 新顶层窗 `'temp'` 出现，`=== RESULT: PASS ===`。
- **根因**：**UIPI**（见 §2.5）—— CurSeen 自提权（High IL），普通权限的注入被**静默丢弃**。
  **产品代码没有问题**；坏的是验收环境。
- **判据**：要区分"注入没送达"与"功能坏了"，**必须带一个已知能改 UI 状态的注入点击作对照**。
  对照组也无反应 = 环境问题（探针没提权）；对照组有效而按钮没反应 = 产品问题。
  配套：在 `on_click` 里加一行诊断日志（如 `打开临时目录：<路径>`），它把"**按钮没被点到**"
  与"**点了但系统没照做**"分开 —— 本次正是靠"日志里一条都没有"才敢把结论钉在 UIPI 上。

### 7.11 按颜色定位控件，不能取"全部同色像素的包围盒"（2026-09-27）

探针用强调色定位按钮，第一版取**所有**强调色像素的包围盒 ⇒ 算出的中心落在内容区的空白处，
连点两次都点空。真因：左侧导航的 **3px 选中指示条**同属强调色，被一并框进了包围盒。

**修法**：按**行内连续色段**找（连续宽 > 40 且按行成组、取最大组）——一次同时排掉细指示条
与零散的抗锯齿像素。定位类判据别用"全局极值/包围盒"，要用**结构**（行内连通段）。

### 7.12 切"生产代码段"的锚点必须精确到 `mod tests`（2026-09-27）

`include_str!` 会把测试自己也包进来，所以要切掉 `#[cfg(test)]` 之后那一段（§2.8）。但
`find("#[cfg(test)]")` 会命中**更早**出现的孤立 `#[cfg(test)]` —— 本例是 `MODULE_NAMES` 上那个
属性 ⇒ 切出来的"生产代码"只剩开头的文档与 `use`，后面每条 `contains(...)` 断言**恒假**。

- 本次落在**幸运方向**（2 条新测试直接红）；若断言写成**否定型**（"不含 X"），同一 bug 就是
  **恒真的假绿**——最坏的那一类。

**锚点取 `"#[cfg(test)]
mod tests"`，切不到就 panic**，不要用裸的 `#[cfg(test)]`
（旧断言当时**碰巧**通过，只因文档注释里提过那个名字 —— 假绿的另一副面孔）。
### 7.13 Lua 脚本验收：查「指令流」才看得见坏参数，但三个坑都在判据自己身上（2026-09-27）

**手段**：把宿主助手 + `ctx` 原语注入一个真 Lua VM，跑**真实脚本**，把每帧产出的绘图指令
（类型 / 坐标 / 颜色 / alpha）全量抓下来再下断言（一次性探针在 `temp/lua_trail_*.py`）。
不改任何 Rust 源码，纯脚本侧验收。

- **它抓到的真 bug**：`tube_chain.lua` 写了 `local r, g, b = colors[c]` —— **Lua 的表不是多值**，
  这行只让 `r` 拿到整张表、`g`/`b` 为 `nil`，于是 `radial` 的颜色参数成了「一个表 + 两个 nil」。
  **语法全过、能跑、每帧 45 条指令计数正常**，只有"逐参数位查类型"才看得见。
  判据：每条指令除 `polygon.points` / `layer` 外，**所有参数位都必须是数字**（表 / `nil` 即红）。
- **坑①：别用聚合量测单体行为。** 用"y 重心"判气泡上浮 —— 寿命到期的气泡从**顶部**被删，
  删一个就把重心往下拉 ⇒ 得到"一半帧往上、一半往下"的假象。正解是**跨帧最近邻追踪同一颗**。
- **坑②：别用包围盒测宽度。** 墨笔四边形 `[a+n·wa, b+n·wb, b−n·wb, a−n·wa]` 的包围盒是
  `max(段长, 2·half_width)`，快移时被**段长**主导 ⇒ 判出"越快越宽"的反向结论。
  正解：量**第 2、4 条边**（横截边），那才是笔宽。
- **坑③：取样窗口要避开已进入终态的尾部。** 链式弹簧的"空闲归零"要冻结 **5 秒**才收敛
  （40 帧时第 14 个节点还没停笔）；而"数三链球珠"若取尾部 20 帧，取到的正是**已归零**那段 ⇒ 数到 0。

**铁律**：断言前先问"这个量会不会被集合的增删污染"；测形状就用**与行为定义同源的量**
（宽度量横截边、上浮追踪单体）；取样区间先确认它还在活跃期。

### 8.1 现行文档只写「现在是什么」与「该怎么做」（2026-09-27）

不写"某目录曾经存在 / 已不存在"这类**考古叙述**（读者不需要，且会让文档自己显得不可信），也不写
会随版本漂移的实测数字（测试条数 / 耗时 / 体积）——**要数字就现场跑一遍**。同类错位还有"与现状
相反"（文档写着"手动补 LICENSE"，实为自动同步）与"死引用"（指向不存在的路径）；改写时保留防坑
信息（如"`temp/` 是一次性区"），只去掉日期戳与审计口吻。门禁 `test_current_docs_carry_no_archaeology`。

### 8.2 同一文件的多次编辑要**逐条串行**下发（2026-09-27）

Edit 是"读-改-写"，对同一文件并发下发两个编辑会**互相覆盖**，表现是两个都报 success、
但只有一个落盘。改完用 `grep -c` 逐条复核。

### 8.3 同一件事写两处就是冗余（2026-09-27）

`HISTORY.md` 一度长到 1357 行，其中 `## 2.0.0` 一节独占 1340 行 —— 每次落地的实测过程被整段抄了
进去，而同样内容早有一份（**两份文件的条目标题逐条对应，就是"写重了"的信号**）。
**分工**：`HISTORY.md` = 版本要点（"这一版有什么"）；**本文 = 坑与教训**；`docs/DESIGN.md` =
设计结论；过程 / 转储 = 根 `temp/`（不入库）。门禁 `test_controlled_docs_stay_concise` 盯篇幅：
根文档与各 README ≤ 400 行、其余专项技术文档 ≤ 800 行；**踩坑记录是分册的**，每册 ≤ 500 行，
**册数不限** —— 写满就新开一册，不为新条目去删旧条目腾地方（2026-10-02 起）。

## 九、录制与媒体（Media Foundation）

### 9.1 `IMFSourceReader` 的流下标由**文件**决定，不是"先 `AddStream` 的就在 0"（2026-09-30）

**现象**：视频裁剪窗预览全黑（探针口径"读不到画面尺寸"）；时长读得出、裁剪产物能播，只有预览瘸。

**根因**：预览解码写死了下标 0（`GetNativeMediaType(0,0)` / `SetCurrentMediaType(0,…)` /
`ReadSample(0,…)`）。自家录屏写盘时视频先 `AddStream`，但**文件解析回来是音频 = 0、视频 = 1**
（reader 按源文件轨道顺序报）——跑到音频流上问 `MF_MT_FRAME_SIZE` ⇒ 空，一条预览都出不来。

**判据**：凡拿流的地方都用"扫描后返回的下标"，**不许写字面量 0**；`RUST_LOG=debug` 会打印
`视频流 N，音频流 …`，配 `cargo run --release --example mp4_probe -- <mp4>` 一次现形。

**同类**：`MFStartup` 必须有人起过——录制线程之外跑任何 MF API，在"本次会话没录过"时全部静默失败
（表现为"选了文件没反应"）。离开录制线程的入口一律自带 RAII 守卫（`platform::mp4_trim::MfGuard`）。

### 9.2 要 MF 吐 RGB32 的三条硬要求 + 一次行序约定（2026-09-30）

缺一条就 `MF_E_INVALIDMEDIATYPE`（`0xC00D36B4`），且**都不报错只说"格式不支持"**：①建 reader 时
就要 `MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING=1`（允许它插色彩转换器）——**事后补设
无效**，属性只在建 reader 那一刻读；②输出类型必须 `native.CopyAllItems` **整包**拷原生属性再换
SUBTYPE（只给 MAJOR/SUBTYPE = 残缺类型）；③必须显式 `MF_MT_DEFAULT_STRIDE = w*4`（RGB 步长有正负
两种布局，MF 不肯替你猜）。

行序同理反直觉：MF 的**正** stride = 顶行在前（top-down），与 GDI DIB（正 = 底行在前）**相反**。
通道序是 B,G,R,A。只查"中心像素非 0"查不出翻行/错色，要落到 PNG 看图。

### 9.3 `IMFSinkWriter` 的两个离线重写陷阱：节流与预建轨道（2026-09-30）

**① 默认按播放速率节流**：`MFCreateSinkWriterFromMediaSink(sink, None)` 走默认属性，写样本**睡到
"该帧该呈现的时刻"**才返回——13s / 13MB 的录屏，分段计时（`read_raw` / `WriteSample` 各累计一次）
一眼分账：读 **0 ms**、写 **155,441 ms**，用户看起来就是"保存卡死"（磁盘上留 79 字节空壳是进程被
杀、`moov` 没写）。修法：建 writer 时给 `MF_SINK_WRITER_DISABLE_THROTTLING = 1`，**155.4s → 0.29s**。

**② `MFCreateMPEG4MediaSink` 的第 2/3 参是"预建轨道"**：传了视频/音频类型，sink 先建好轨道 0/1，
再 `AddStream` 就追加成 **4 条轨、前两条零样本**——播放器默认挑第一条视频/音频轨 ⇒ **黑屏 + 无声**；
MF SourceReader 是扫描式的，自家探针照样解得出真轨，**很容易误判文件没坏**。修法：第 2/3 参传
`None`，轨道一律 `AddStream`（门禁 `sink_is_created_without_pre_seeded_tracks`）。

教训：**离线重写 ≠ 采集**（节流对"边录边播"是对的）；分段计时是"慢得离谱"的最快分诊——先把时间
记到具体调用上，别急着猜解码/编码。写盘起工作线程（`defer_blocking` 在 UI 线程跑）+ `Arc<Mutex<..>>`
传进度，UI 侧 `on_interval` 收尾——工作线程一律不碰 `Rc<RefCell<..>>`。

### 9.4 录制收尾绝不能 join 在 UI 线程上（2026-10-02）

**现象**：录屏时间一长，按停止快捷键没反应、面板也打不开，整个程序冻结；任务管理器杀进程，产物
缺 `moov` 打不开。

**根因**：`stop_recording_now` 在 UI 线程同步 `finish()` → `join` 录制线程，而录制线程可能被编码
器（`WriteSample` / `Finalize`）无限期卡住。join 一等，主消息循环停摆——快捷键、面板、托盘全死；
强杀进程 = `Finalize` 没跑 = 不可播放。

**判据**：UI 线程只发停止位（`finish_detached`：后台线程限时 join，超时弃子），结论经全局槽位回
UI 帧循环补日志/提示/裁剪；退出路径允许**有限**等待（35s 上限）。凡"可能不返回的收尾"一律不许同步等在任何有消息循环的线程上。

### 9.5 录制线程会**楔在循环里**：不报错、不写帧、停止位也唤不醒（2026-10-02）

**现象**：录制线程可能永久停住（实测两次：223 秒第 6690 帧、9.5 秒第 285 帧，都停在
`AcquireNextFrame`）—— 无错误、无 trace、文件停止增长，界面却显示"在录"。概率性、与时长无关（`long_record_never_wedges`）。
**根因在驱动层**：两次现场 `timeout` 都 ≤500ms，而它十几分钟没回来 ⇒ **DXGI 的超时到驱动那一层
不兑现**；磁盘、重试死循环、时间溢出、句柄泄漏、音频死锁、放大镜合成、显卡 TDR 均排除。
**配套**：① 阶段心跳（`RecStage`）停摆 15 秒报"卡在「抓帧/拷帧/画光标/写视频/写音频/收尾」第 N
帧"；② 停摆 60 秒主动结束（只对 MP4 且出过帧生效，GIF 不能被误杀）；③ `pump` 改成
`AcquireNextFrame` 返回 `Ok` 就 Release。**"线程卡住"本身必须可观测**。

### 9.6 卡死时**栈展开守卫救不了产物**：sink 要能被别的线程接管（2026-10-02）

**坑**：`SinkFinisher` 守卫活在录制线程自己的栈上，出错栈展开才会 `Finalize`；线程卡死则栈永不
展开 ⇒ 产物必然缺 `moov`（几百 MB 也播不了）—— 9.5 两次废文件的直接成因。

**判据**：凡"靠栈展开兜底的收尾"都要问一句"线程卡住时谁来收"。修法：`IMFSinkWriter` 登记一份到
`Recorder` 的 `SinkSlot`，守卫与槽位共用同一个 `Option`——谁先拿到谁收，绝不收两次；收尾线程确认
"卡在采集侧"就自己 `Finalize`（编码/音频/收尾阶段**不能**接管）。回归锁 `wedged_record_still_yields_a_playable_mp4`，已反向验证会红。

### 9.7 楔住之后的两件**确定性**加固（2026-10-02）

驱动层的永久阻塞应用层根除不了，但两处自己埋的隐患可以直接拆，且**不依赖复现**。
**① 采集永不阻塞等待**：节拍本就由循环末尾 `sleep_until` 独占，原写法却把"离截止还剩多久"当
`AcquireNextFrame` 的超时（≤500ms），白送一条永久阻塞路径。改传 **0**：只问"现在有没有新帧"、
立即返回；它返回的是"自上次取帧以来的累积更新"，33ms 内有变化照样拿得到（实测 30.1fps 不漏帧）。
**② 编码器用独立纹理** `Session::enc`：`acq` 原本**同时**被 GDI（每帧 `GetDC` 画光标）与 MF 的
异步 MFT 读取。"一张纹理同时给 GDI 与 D3D 异步消费者"是明令禁止的互操作组合，特征正是概率性、
不可复现、然后永久卡住。解法：拷一份到 `enc`（不带 `GDI_COMPATIBLE`）再交给 MF。

### 9.8 桌面复制失效重建：**必须先释放旧的再建新的**（2026-10-03）

**坑**：`DXGI_ERROR_ACCESS_LOST`（显示器重排 / 驱动重置 / 分辨率变化）的重建分支原先是
"先 `DuplicateOutput` 建新的，成功了再赋给 `self.dupl`"——旧对象此刻还活着，于是这一步**恒**返回
`0x80070057 E_INVALIDARG`，重建 100% 失败。也就是说"切显示器 / 改分辨率"这种天天发生的事件，
等于录制直接报错终止。

**实测（本机，非文档结论）**：

| 顺序 | 结果 |
|---|---|
| 第一个 duplication | ok |
| 手上还活着它时再建（**同设备**） | ✗ `0x80070057` |
| 手上还活着它时再建（**换新设备**） | ✗ `0x80070057` |
| **先 `ReleaseFrame` + 丢弃旧的，再建** | ✓ ok |

**判据**：DXGI 同一时刻**全进程只容一份**桌面复制，且它**不会**把先前的挤掉——撞上限就是直接失败。
换设备不是出路（这一条否掉了"卡死了换台设备重连采集"的自愈设想）。凡"失效后重建"的代码，
一律**先释放、再新建**，并把这条顺序收进一个可单测的方法（`DuplHolder::replace`）而不是散在分支里。
顺带：`0x80070057` / `0x887A0007` 属**非瞬时**失败，重试 10 次 × 50ms 只会掩盖真相，已改为立刻返回
并在错误串里点明"同一时刻只容一份"。回归锁 `rebuild_drops_the_old_duplication_before_building_a_new_one`
（纯逻辑，已反向验红）+ `rebuilding_a_duplication_needs_the_old_one_gone_first`（真机跑驱动）。

### 9.9 长录楔死是**概率性**的，而自救若挂在覆盖层上则**一次都不执行**（2026-10-03）

§9.5 记了"录制线程会楔在循环里"这个现象。这里补两件那节没定下来的事。

**① 楔死时长不稳定 ⇒ 它是概率性驱动层阻塞，不是"跑满 N 分钟必现"。**
`rec_stress`（headless 探针，1/10/30/60/120 分钟五段）两轮实测：

| 段 | 轮次 1 | 轮次 2 |
|---|---|---|
| 60 秒 | PASS | PASS |
| 600 秒 | PASS | PASS |
| 1800 秒 | **楔于 458s**（帧数冻结在 13767，停摆持续 441s） | **楔于 920s**（25812 帧） |

同一台机、同一个二进制，楔点从 458s 挪到 920s ⇒ **没有"到点必现"的阈值可赌**，
也不能靠"录短一点就安全"来规避。两次都卡在 `AcquireNextFrame`（timeout 已传 0），
属驱动层永久阻塞，应用层能做的只是**止损**（保住已录部分）而不是**预防**。

**② "停摆 60 秒主动结束"那条自救挂在 `Runtime::frame()` 里 ⇒ headless 探针跑不到。**
`frame()` 只在覆盖层 `paint()` 中被调，而探针不起覆盖层 —— 于是一段楔住后
`rec_stress` 会**永远等下去**（轮次 1 干等到手动 `taskkill`）。
凡"靠上层帧循环兜底"的止损，都必须问一句"**这一层不在时会怎样**"：
要么下沉进 `Recorder` 自身，要么在探针里复刻同一判据（`rec_stress` 选了后者，
并注明它与 `REC_STALL_GIVEUP_MS` 同值、为什么不直接引用那个常量）。
收尾侧另有上限：`Recorder::finish()` 的 `FINISH_WAIT` = 35s，且卡在采集阶段时会
接管 `Finalize` 抢救（§9.6）—— 所以"自救 → 收尾"这条链在楔住后是能走完的。

## 十、Lua 脚本扩展（2026-09-30 起）

**① 热键绕过启用开关**：键位写在 `params[id].hotkey`、启用状态在两张 active 列表，是两条互不相干的
持久化链路，而派发侧只读前者 → 名单在派生时就按启用过滤（`script_hotkeys_with_state`），同一份名单
同时喂 `handle_action_key`（派发）与 `action_hotkey_wakes`（park 唤醒）。

**② thread_local 挡不住"每次新线程"**：重复按同一热键冒出一串同样的窗——"已开一窗"记在
thread_local，而 `run_ext_detached` 每次 spawn 新线程，那份状态恒为空 → 去重做在派发器
（`ext_runner::try_claim` 进程级登记表，守卫 `Drop` 归还）；标识用**句柄不用标题**（标题随状态变，
漏判且不报错）。

**③ 缺失的回调 = 可选，不是错误**：一次性脚本只有 `schema` + `run`，取回调别写
`let f: Function = globals.get("init")?`，会把"它不关心"报成 `convert nil to function`。

**④ 界面注释只写"这个控件是干嘛的"（2026-10-01 用户口径）**：设置页「快捷键」卡体第一行的
`card::note`（一把键只能给一个功能…）删掉——互斥实现正确，但那是**改键那一刻才发生一次**的
内部行为，平时白占一行，逻辑上它"静默生效"，不需要被解释；让实际表现（旧绑定变「（空）」）自己说话。

**⑤ 开关镜像了，键位没镜像（2026-10-01）**：两条链路（固定字段 `HotkeyField` / 脚本参数 `hotkey`）
的互斥早就互通（`set_hotkey_exclusive` ↔ `set_script_hotkey_exclusive`），只是界面上脚本热键看不见 →
补「脚本快捷键」集合卡，行名 = **脚本名 > 参数名**（两段都用现成文本：脚本显示名 + 参数单元
`label`），行内仍绑脚本自己的 sig、走 `host_signal` 跟着参数重建，不新增任何逻辑。

**⑥ 工具顺序只写一份（2026-10-01）**：工具栏按钮序、屏幕页「快捷键」行序、设置页集合表行序同 =
`core::hotkeys::DRAW_TOOL_ORDER`（橡皮擦在马赛克**右边**）。出厂键位一个没变（1/2/3/5/6/7/8/9/
0/4，序号留空），变的只是界面排布；三处手抄必走偏，故顺序只留正本、另两处照抄，由
`button_order_matches_the_hotkey_order` 与 `screen_hotkey_rows_follow_the_tool_order` 钉住。
